## 1. Executive decision

V006 is materially improved and its physical package is clean, but it does **not** close the V005 review safely enough to become the accepted UraiFlow baseline.

Five release-blocking defects were independently reproduced against the code extracted from the received ZIP:

1. An unresolved `UncertainCommit` can be converted from `COMPENSATION_FAILED` to **false `ROLLED_BACK`** by `RecoveryService.retry_rollback`, while the external effect remains.
2. An adapter may perform the external side effect and then raise a timeout/exception; V006 records no uncertainty and again reports **false `ROLLED_BACK`**.
3. Duplicate display names—explicitly allowed by ADR-0010—can overwrite each other in rollback-capability preflight, allowing a non-rollback-capable adapter to commit before a later failure.
4. Content already confirmed by the human remains mutable and can be changed after confirmation but before commit; the altered, unapproved value is committed successfully.
5. The final shipped ZIP cannot reproduce its own G10 PASS. `validate_docs_consistency.py` fails on a clean extraction, even though the manifest-protected shipped evidence says G10 PASS.

V006 also has high-priority immutability, audit, version-consistency, evidence-hygiene and documentation-navigation defects. These are detailed below.

**Release decision:** do not accept, freeze, deploy, or build persistence/provider work on V006. Correct these defects in **V007**, without feature expansion.

# 4. Release-blocking findings

## P0-1 — Recovery converts an unresolved uncertain commit into false `ROLLED_BACK`

### Contract that V006 claims

ADR-0017 states that an uncertain external commit must block `ROLLED_BACK`, and that `ROLLED_BACK` means no committed external effect remains unaccounted for:

- `02-architecture/adr/ADR-0017-uncertain-external-commit.md:27-41`
- `BUILD-REPORT-V006.md:20-24`
- `06-traceability/RTM-V006.md:66,72`

### Defective implementation

`RecoveryService.retry_rollback` iterates only over `proposal.unrecovered_receipts`. When that tuple is empty, it clears the same tuple and advances directly to `ROLLED_BACK`. It never checks `proposal.uncertain_commits`:

- `src/uraiflow/recovery/service.py:62-76`
- `src/uraiflow/recovery/service.py:98-117`

The state transition itself also has no aggregate invariant preventing `ROLLED_BACK` while uncertainty remains:

- `src/uraiflow/proposal/model.py:35-68`
- `src/uraiflow/proposal/model.py:167-172`

### Independent reproduction

1. Adapter performs a real external side effect.
2. Adapter returns an invalid receipt.
3. V006 correctly enters `COMPENSATION_FAILED` with one `UncertainCommit` and zero `unrecovered_receipts`.
4. An authorised operator calls `retry_rollback`.
5. V006 performs zero rollbacks, changes the status to `ROLLED_BACK`, and leaves both the external effect and the uncertain record present.

Observed result:

```text
Before retry:
  status=COMPENSATION_FAILED
  external effects=1
  unrecovered receipts=0
  uncertain commits=1

After retry:
  status=ROLLED_BACK
  external effects=1
  retry compensated=0
  uncertain commits=1
```

### Impact

This directly reopens the exact class of defect ADR-0017 was created to close. A false terminal recovery state can tell operators and downstream systems that no external effect remains when one actually does.

### Required V007 correction

- Make the aggregate enforce the invariant structurally: no path may enter `ROLLED_BACK` while either `unrecovered_receipts` **or** `uncertain_commits` is non-empty.
- Replace generic public `advance(ROLLED_BACK)` with a guarded aggregate command such as `mark_rolled_back()` that verifies both collections are empty.
- `retry_rollback` must remain `COMPENSATION_FAILED` when uncertain commits exist, even when all trusted receipts have been rolled back.
- Uncertain commits require a separate reconciliation operation, or evidence-backed manual resolution; `retry_rollback` cannot silently clear or ignore them.

Required regression:

```text
test_retry_rollback_cannot_clear_or_ignore_uncertain_commits
```

## P0-2 — Exception after external side effect also produces false `ROLLED_BACK`

### Defective implementation

V006 creates an `UncertainCommit` only when `adapter.commit()` returns and receipt validation fails:

- `src/uraiflow/pipeline/orchestrator.py:208-243`

When `adapter.commit()` raises, V006 records only a failure string and breaks:

- `src/uraiflow/pipeline/orchestrator.py:201-207`

Because the failing operation is absent from both `committed` and `uncertain`, V006 advances to `ROLLED_BACK` when earlier trusted rollbacks have no failures:

- `src/uraiflow/pipeline/orchestrator.py:259-295`

### Independent reproduction

The test adapter performs the external write and then raises:

```python
self.effects.append(record.record_id)
raise TimeoutError("response lost after remote commit")
```

Observed V006 result:

```text
status=ROLLED_BACK
external effects=1
uncertain commits=0
recovery report uncertain commits=0
failure="raises: TimeoutError: response lost after remote commit"
```

### Impact

A timeout, connection reset, lost response, process interruption, or provider exception after dispatch does not prove that the remote system did nothing. Treating such failures as definitely uncommitted creates false rollback claims in normal distributed-system failure modes.

### Required V007 correction

The adapter contract must distinguish **definite non-commit** from **unknown outcome**:

- Default any exception after invoking the external commit boundary to `UNKNOWN/UNCERTAIN`.
- Permit a narrowly typed exact exception, for example `DefinitelyNotCommitted`, only when the adapter can prove no side effect occurred.
- Add idempotency-key status lookup/reconciliation to the production adapter contract, or an explicit `reconcile_uncertain_commit` operation.
- Record trusted request-side identity for exception-based uncertainty exactly as for invalid receipts.
- Ensure the aggregate cannot reach `ROLLED_BACK` until every unknown result has been reconciled.

Required regression:

```text
test_exception_after_remote_side_effect_is_recorded_as_uncertain
```

## P0-3 — Duplicate display names bypass rollback-capability preflight

### Governing contract

ADR-0010 is explicit:

- display names are presentation-only;
- duplicate display names are permitted;
- display names must never affect routing or rollback.

See `02-architecture/adr/ADR-0010-adapter-machine-identity-and-receipt-trust.md:13-23`.

### Defective implementation

Rollback preflight builds a dictionary keyed by the display name:

- `src/uraiflow/pipeline/orchestrator.py:303-322`

```python
registered_by_name[registered.descriptor.name] = (
    registered.descriptor.supports_rollback
)
```

When two different adapters share a display name, the later adapter overwrites the earlier adapter's capability.

### Independent reproduction

- Adapter A: ID `adp.nonrollback`, display name `same-display`, rollback unsupported.
- Adapter B: ID `adp.second`, display name `same-display`, rollback supported; commit then fails.
- Both names are valid under ADR-0010.
- Adapter B overwrites Adapter A in the preflight dictionary.
- Preflight does not block.
- Adapter A commits a real effect.
- Adapter B fails.
- Adapter A cannot be rolled back.

Observed result:

```text
preflight_blocked=False
status=COMPENSATION_FAILED
nonrollback_external_commits=1
```

### Impact

The atomic multi-record guarantee can be defeated by a display-name collision that the architecture explicitly allows.

### Required V007 correction

- Key preflight by `descriptor.adapter_id`, never `descriptor.name`.
- Prefer iterating immutable registration records without lossy dictionary aggregation.
- Use name only as additional human-readable evidence.
- Add a regression with duplicate display names and different rollback capabilities.

Required regression:

```text
test_duplicate_display_name_cannot_mask_nonrollback_adapter
```

## P0-4 — Human-confirmed content is mutable and different content can be committed

### Claimed boundary

The product boundary says UraiFlow proposes records, a human confirms them, and only the confirmed proposal is committed. `Proposal` documentation states that content mutation occurs through governed aggregate commands:

- `00-control/PROJECT-START.md:12-18`
- `src/uraiflow/proposal/model.py:115-122`
- `src/uraiflow/confirmation/service.py:1-15`

### Defective implementation

`Proposal.items` is a mutable list. Each `ProposalItem` is mutable, and its `fields` value is a mutable dictionary:

- `src/uraiflow/proposal/model.py:83-112`
- `src/uraiflow/proposal/model.py:124-139`

The commit path trusts current mutable `status`, `decision`, record type and fields; it does not compare them with an immutable confirmed snapshot/version:

- `src/uraiflow/pipeline/orchestrator.py:178-200`

### Independent reproduction

1. Ingest proposal containing title `approved`.
2. Call the governed `confirm_all()` command.
3. Change `proposal.items[0].fields["title"]` directly to `NOT_APPROVED`.
4. Call commit.
5. V006 commits `NOT_APPROVED` successfully.

Observed result:

```text
confirmed_value="approved"
committed_value="NOT_APPROVED"
status=COMMITTED
failure=None
```

A second probe also demonstrated that direct writes to `item.decision` and `proposal.status` can bypass the confirmation service entirely and still commit.

### Impact

The system cannot prove that the external record is what the human approved. This breaks the central human-in-the-loop safety boundary and creates an audit falsehood.

### Required V007 correction

- On confirmation, create a **deeply immutable confirmed snapshot** containing record IDs, types, field values, confidence/source references and a canonical content hash/version.
- Commit only that confirmed snapshot—not the live mutable proposal list.
- Make `status`, decisions, items and recovery fields private aggregate state with read-only views.
- Any content change after confirmation must invalidate the confirmed snapshot and return the proposal to revalidation and reconfirmation.
- Include the confirmed snapshot/version/hash in lineage and receipt-binding evidence.
- Make internal state transitions non-public implementation details; application code should use governed commands only.

Required regressions:

```text
test_post_confirmation_content_change_cannot_be_committed
test_direct_status_and_decision_writes_cannot_bypass_confirmation
test_commit_uses_exact_confirmed_snapshot_version
```

## P0-5 — The final ZIP's G10 fails although shipped evidence says PASS

### Shipped claim

The manifest-protected file `evidence/G10-docs-consistency.txt` inside the received ZIP states:

```text
G10 docs-consistency PASS: ... build-report facts regenerate identically from machine evidence
```

### Why the shipped artifact fails

`gen_build_report.py` derives the manifest row from `evidence/G01-manifest-check.txt`:

- `scripts/gen_build_report.py:22-40`
- `scripts/gen_build_report.py:60-62`

The packager deliberately removes that file from the payload:

- `scripts/package_release.py:49-59`

The clean-extraction smoke runs only pytest, starter validation and manifest check. It does **not** run G09 or G10:

- `scripts/package_release.py:145-176`

Therefore the build report contains `Manifest contract | PASS`, but on the final ZIP the evidence file used to generate that word is absent. `gen_build_report.py --check` regenerates `see evidence`, detects drift, and G10 fails.

### Independent clean-extraction result

```text
manifest check: PASS (239 files, full contract)
G10 build-report drift: machine facts do not match evidence
G10 docs-consistency FAIL:
 - build report drift: machine facts do not regenerate identically from evidence
```

### Impact

The final artifact contains a false PASS result for a mandatory release gate. The attestation is still valid for the three smoke steps it actually ran, but it does not prove G10 on the final artifact. V006 cannot be accepted under its own release policy.

### Required V007 correction

- Make G10 reproducible on the **final clean-extracted ZIP**, not only in the source/build tree.
- Stop generating build-report manifest status from an evidence file that packaging removes. Derive it from the actual manifest/check, or represent it explicitly as external-attestation evidence.
- Add non-mutating `--check` modes to G09/G10 where needed.
- Extend exact-final-ZIP smoke to run at least G09 and G10, and fail packaging if either fails.
- The attestation must record those final-ZIP results.
- Add a clean-extraction regression that constructs the governed payload with excluded self-referential evidence and proves G10 still passes.

Required regression:

```text
test_final_packaged_zip_reproduces_g09_and_g10
```

# 5. High-priority findings

## P1-1 — The pinned adapter descriptor is not deeply immutable

`AdapterDescriptor` is a frozen dataclass, but `required_fields` is converted to a normal mutable dictionary:

- `src/uraiflow/adapters/contract.py:25-72`

`RegisteredAdapter` stores that same descriptor object and calls it immutable:

- `src/uraiflow/routing/registry.py:23-35`
- `src/uraiflow/routing/registry.py:44-63`

Independent probe:

```python
pinned.required_fields["task"] = ()
```

Observed behaviour:

```text
before mutation: missing title is invalid
post mutation:  missing title is valid
same pinned descriptor object: True
```

This does not require private-state access or `object.__setattr__`; it is ordinary dictionary mutation.

**Required correction:** registry must construct and own a deep canonical contract snapshot. Use recursively immutable values (`MappingProxyType` over a defensive copy, tuples, or another stdlib immutable representation), validate `supports_rollback` as exact `bool`, and expose only immutable views.

Required regression:

```text
test_registered_descriptor_is_deeply_immutable
```

## P1-2 — Lineage/audit events are not immutable

`LineageEvent` is frozen only at the top level. Its `payload` is stored by reference as an arbitrary mapping, and `LineageStore` stores and returns the same event object:

- `src/uraiflow/lineage/model.py:21-42`
- `src/uraiflow/lineage/store.py:13-33`

Independent probe appended manual-resolution evidence and then modified the original payload dictionary. The already-stored audit event changed to:

```text
operator_id="forged"
evidence="rewritten"
```

This contradicts the module's “immutable lineage/audit events” and “append-only” claims.

**Required correction:** validate payload schema, make a recursive defensive immutable copy at event construction/storage, and return immutable snapshots. Also require timezone-aware timestamps and decide whether all times are normalized to UTC.

Required regression:

```text
test_lineage_payload_cannot_change_after_append_or_read
```

# 8. Required V007 scope and acceptance conditions

V007 must be a **correction-only hardening release**. Do not add persistence, real providers, NEEDS_CLARIFICATION workflow, role models, or feature expansion until these defects close.

## Required architecture corrections

1. **Structural recovery invariant:** `ROLLED_BACK` is impossible while trusted unrecovered receipts or uncertain commits remain.
2. **Explicit commit outcome model:** definite rejection vs unknown/uncertain external result; timeouts and post-dispatch exceptions default to uncertain.
3. **Machine-identity-only preflight:** rollback capability aggregated by `adapter_id`, never display name.
4. **Immutable confirmation snapshot:** commit uses the exact content/version approved by the human; any mutation invalidates confirmation.
5. **Deep immutable registration contract:** registry owns a canonical immutable copy of descriptor fields and capabilities.
6. **Deep immutable audit event:** lineage payload is defensively copied/frozen and cannot be rewritten through caller or returned references.
7. **Final-artifact gate reproducibility:** G09/G10 pass inside the exact final clean-extracted ZIP and are recorded in the attestation.
8. **Single version source and clean evidence namespace:** runtime, project, manifest and docs agree; stale generic evidence is removed/versioned.
9. **Current-document reference validation:** reading map, RTM history and build-report references all resolve.

## Required red-state proof

Before fixing, V007 evidence must execute the independent probe shapes against pristine V006 and show each defect:

- uncertain retry → false `ROLLED_BACK`;
- exception after side effect → false `ROLLED_BACK`;
- duplicate display name → preflight bypass;
- confirmed content mutation → changed value committed;
- descriptor mapping mutation → validation changes;
- lineage payload mutation → stored audit changes;
- clean final ZIP → G10 failure;
- runtime version mismatch.

## Required green regressions

At minimum:

```text
test_retry_rollback_cannot_clear_or_ignore_uncertain_commits
test_exception_after_remote_side_effect_is_recorded_as_uncertain

test_lineage_payload_cannot_change_after_append_or_read

test_runtime_version_matches_pyproject_and_manifest
test_current_document_references_exist
```

## Required release output

