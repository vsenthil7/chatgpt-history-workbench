## Executive decision

The uploaded archive is healthy: ZIP CRC checks pass, the manifest accounts for every declared payload, all declared byte counts and SHA-256 hashes match, the nested repository parses and compiles, and the DOCX/XLSX artefacts open. The problem is not the upload.

The release itself has four blockers and several high-severity defects. Most importantly:

1. The delivered deterministic test suite is red: `1 failed, 630 passed, 1 skipped, 2 deselected` because the clean-environment CLI test omits the new `at-durable` package.
2. A database carrying a current event-store marker and an incompatible old identity-store marker is still accepted by the event store.
3. The real CLI can write events and provenance before the identity registry rejects that same incompatible database, leaving a partial import committed.
4. A matching sibling marker can authorise adoption and modification of a malformed target-store schema.
5. The included mutation runner can report every mutant killed even when the unmutated baseline already fails.
6. The accepted input domain of the canonical encoder is not injective for Python subclasses; two unequal `SourceRef` values can produce one Event ID.
7. Release facts, current metadata and the included release-builder do not establish a reproducible final seal.

No six-status evidence work, timeline work, commitments work, questions work or other feature tranche should start. V036 must be a corrective release only.

### F02 — BLOCKER — Mixed identity schemes are accepted in a shared database

V035 claims every durable store refuses a database written under another identity scheme before any read or write. The delivered policy does not enforce agreement across all marker tables.

`inspect_database()` records only one `sibling_scheme`. `decide_open()` checks the sibling only when the target store has no own schema marker. Once the target store's own schema/version/scheme are valid, an incompatible sibling marker is ignored.

**Reproduced both directions**

1. Valid V035 event marker `schema_meta: schema 3, atid/3` plus identity marker `identity_meta: schema 1, atid/1` → `SqliteEventStore` opens.
2. Valid V035 identity marker `identity_meta: schema 2, atid/3` plus event marker `schema_meta: schema 3, atid/1` → `SqliteIdentityRegistry` opens.

Therefore a file can advertise two incompatible identity schemes and still be accepted.

**Real CLI impact**

A database was prepared with a current event marker and an older identity marker, then passed to the real import path. Before rejection it contained zero events, zero source registrations and zero import occurrences. After the identity registry finally rejected the old schema, it contained:

```text
2 events
1 source_registration
1 import_occurrence
```

Failure path:

```text
CLI import
  ├─ opens EventStore
  │    └─ sees own atid/3 marker and ignores sibling atid/1 marker
  ├─ writes source registration, occurrence and events
  └─ opens IdentityRegistry
       └─ rejects old identity schema

Result: command fails, but partial durable state remains committed.
```

This is direct database-integrity damage and disproves the release verdict's “before reading or writing a byte” claim.

**Required closure**

- Inspect every platform marker table and retain every observed scheme, not one overwritten sibling value.
- Reject any disagreement among platform markers before opening any store.
- Add a CLI-level shared-database preflight that validates all stores before the first write.
- Either coordinate the import under one atomic transaction or ensure no component can write until all store preflights pass.
- Assert the complete database directory state byte-for-byte before and after every refusal, including WAL/SHM/journal sidecars.

### F03 — BLOCKER — Sibling markers and partial schemas authorise unsafe adoption

A matching sibling marker proves only that another platform store owns the container. It does not prove that existing target-store tables are valid or safe to adopt.

**Reproduction A: matching sibling plus malformed target table**

Database before open:

```text
identity_meta = schema 2, atid/3
source_registration(x TEXT)   # malformed target-owned table
no event-store schema_meta
```

`SqliteEventStore` opened successfully, created/stamped the event store, added the other event-store tables, left the malformed `source_registration(x)` untouched and changed the database bytes.

**Reproduction B: valid own marker plus partial/malformed store**

Database before open:

```text
schema_meta = schema 3, atid/3
source_registration(x TEXT)   # only one malformed known table
```

Because `known_tables` uses intersection rather than full structural validation, one table name is enough. The store opened, created missing tables and modified the database while retaining the malformed table.

**Reproduction C: malformed marker shape**

A table `schema_meta(x TEXT)` leaks raw:

```text
OperationalError: no such column: key
```

instead of a domain-level refusal.

**Required closure**

- With no own marker, allow target-store creation only when no target-owned table, index or trigger already exists.
- With an own marker, validate the complete expected schema: table set, required columns, primary/foreign keys, indexes and marker shape.
- Never silently repair or adopt a partial/corrupt marked store during ordinary open.
- Convert malformed/corrupt marker failures into the declared domain exception without writing.
- Perform schema creation and marker stamping atomically.

### F04 — HIGH — The accepted canonical input domain is still non-injective

The encoder claims injectivity across accepted values, but uses `isinstance()` for strings, integers, datetimes, lists and tuples. Python subclasses can override the operations the encoder trusts.

A `str` subclass was accepted by `SourceRef`. Two unequal underlying values—`different-source-A` and `different-source-B`—overrode formatting and UTF-8 encoding so both canonicalised as `same-source`.

Observed result:

```text
refs_equal = False
source_ids_equal = False
canonical_keys_equal = True
Event IDs:
ea7b181c0d885fc1a23ef4b6576da8ca
ea7b181c0d885fc1a23ef4b6576da8ca
```

This is deterministic identity collapse inside the function's accepted Python domain, not a hash collision.

**Required closure**

- Use exact built-in type boundaries: `type(value) is str`, `type(value) is int`, exact `bool`, exact supported sequence types, and an explicit datetime policy.
- Enforce or normalise exact primitives in public record constructors, not only inside the encoder.
- Add adversarial subclass tests for `str`, `int`, `datetime`, `list` and `tuple`.
- Add a mutation regression that reintroduces `isinstance` and must be killed.

### F06 — HIGH — The claimed 67/67 mutation result is invalid

The mutation runner performs no baseline-green test. For each mutant it runs pytest and treats any non-zero return code as “killed”:

```python
if proc.returncode != 0:
```

The exact unmutated command used by the runner already returns non-zero:

```text

```

It stops at the clean-environment CLI failure. Therefore unrelated baseline failure can mark every mutant as killed. The workbook, README, changelog and release facts claim 67 mutation regressions without evidence that failures are mutation-specific.

**Required closure**

- For each mutant, record the failing test identity and prove the restored baseline returns zero afterward.
- Do not count timeout, environment failure, collection failure or unrelated test failure as a kill.
- Emit a machine-readable mutation report tied to the final source hash.

### F08 — MEDIUM — The atid/3 instant grammar is not fully language-independent

The declared accepted domain includes aware Python datetimes, but `canonical_instant()` delegates year formatting to platform `strftime("%Y...")`.

On the delivered Linux/Python runtime:

```text
year 1   -> 1-01-02T03:04:05.000006Z
year 9   -> 9-01-02T03:04:05.000006Z
year 99  -> 99-01-02T03:04:05.000006Z
year 999 -> 999-01-02T03:04:05.000006Z
```

The specification describes `%Y` but does not publish normative golden bytes for these accepted values. A cross-language implementation may reasonably emit `0001`, `0009`, `0099`, `0999`, producing different IDs.

**Required closure**

- Format every instant component manually, including `year:04d`.
- Publish normative canonical key and ID vectors for all primitive types, Unicode, nested sequences, timezone-equivalent instants and year 1.
- If the representation changes for any previously accepted value, bump the identity scheme and durable markers again; alternatively explicitly reject the unsupported datetime range before identity derivation.
