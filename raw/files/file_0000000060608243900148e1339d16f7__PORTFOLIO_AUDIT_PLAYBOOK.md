# Portfolio Audit Playbook

v3 — 20 September 2026.

Derived from 39 defects found in OnCall Copilot across 28 releases, 20 more found by the first
independent external review (10 blockers), **and 13 more found by the second independent
review and by running v3 of this tool against the remediation** — two of those blockers.
Nearly all 72 were invisible to a 100% coverage gate. Nine sibling products were built with
the same patterns and have not had this applied.

The v2 addition — **the gates did not cover the file that decides what ships** — remains the
most important check. The v3 additions are what a green gate over a *well-built* core still
hides: four defect classes that the second reviewer found in ninety minutes, each one level
down from the class the first reviewer found. Three of them are now mechanical (A10–A12) and
one is advisory (A13). **A10 alone, run against the fixed code, found a 13th defect the
reviewer had missed** (an atomic id allocator with no production caller), which is the best
argument for running the tool after every remediation, not only before.

Run `node audit.mjs <repo>` for the mechanical half, then work the judgement half below.
The script reports **suspects, not verdicts** — every expensive defect was a contract or
integration mismatch that no checker could have decided on its own.

---

## Why coverage missed all of this

Each defect below sat in a module with 100% coverage. Coverage measures whether a line
*executed during a test*, never whether a user can reach it, whether anything calls it, or
whether it matches the platform's real contract.

| Class | What it looked like | OnCall example |
| --- | --- | --- |
| Orphan module | Fully tested, nothing imports it | Five features unreachable; the live slash handler was a stub returning a string |
| Read/write split | Reads one store, writes another | Dashboard read from the repository; incidents were written to an in-process Map |
| Promise without a gate | State maintained, never enforced | Read-only on failed payment set everywhere, enforced nowhere; plan limits never counted |
| Claim without a caller | Module exists, no path calls it | "Encryption at rest" on the trust page; tokens stored in plaintext |
| Scope creep on "fixed" | Correct for one condition, not the deployed one | Id collision fixed for restarts, still live under two replicas |
| Circular evidence | Fake written to match your own code | A self-written Pg fake hid a foreign-key defect for six sprints |
| Platform contract | Your code is fine; the platform disagrees | 3-second slash-command ack; 12-hour token TTL; silent Block Kit truncation |
| **Composition root outside the gate** | Every module is correct; the file wiring them is not built, not tested, and not compiled | `tsconfig` included `src/**` only and jest excluded `scripts/`, so a composition root with four type errors, eight in-memory stores in production, `session: () => undefined` and every async response discarded as an empty `202` sat behind a green 100% suite |
| **A test that encodes the defect** | The suite defends the bug instead of catching it | A security test asserted `expect(status).toBe(202)` with the comment "async shell" — the swallowed-response defect written down as expected behaviour |
| **Sync core, async world** (v3) | Every platform contract returns a value, so the unwired stubs and the core agree perfectly and no test can see the mismatch; discovered only when a real adapter is attempted | PX-001 — four sync interfaces (six, counting OAuth and payments), zero Promises in the feature core; 527 tests at 100% proved the core agreed with its own fakes |
| **Two enforcement methods, one wired** (v3) | A safe atomic method and an unsafe convenience method both exist and are both fully tested; production calls the unsafe one | PX-002 — `claimWrite` tested, `checkWrite`+`recordWrite` shipped, usage never incremented; PX-013 — `claimNext` tested, local counter shipped |
| **Gate by enumeration** (v3) | A boot gate checks a list of providers; the defect is a provider that is not on the list. Omission beats naming | PX-003 — the `response_url` poster (the delivery of every declare result) was a `console.log` closure; `views.open` a bare lambda; the OAuth client a third |
| **Queue without a lifecycle** (v3) | A fix introduces an in-memory queue; the shutdown path predates it and does not drain it | PX-004 — the ack queue created by the 3-second-ack fix was lost on every SIGTERM, i.e. every deploy |

## The judgement half — ten checks, roughly 100 minutes per product

**0. The gate's own blind spot — do this first, it takes two minutes.** Open `tsconfig.json`
(or the equivalent) and the test config. Does the build compile the composition root, the
server entry point and the scripts? Does any test import them? Does coverage collect from
them? If the answer to all three is no, the suite is telling you nothing about whether the
product starts. `node audit.mjs` now reports this as A8/A9. Then run the two commands that
settle it: compile everything, and boot the built artifact.

**1. Reachability.** For every story marked Done, name the user action that reaches it. If you
cannot, it is *module-complete*, not done. OnCall's Done count fell 77 → 70 on this check, then
earned its way back by building the missing surfaces.

**2. Read/write pairing.** For each store, list what writes to it and what reads from it. If a
read path has no matching write path, the feature is permanently empty in production.

**3. Promise tracing.** Open the trust page, pricing page and help centre. For each claim, name
the line of code that *refuses* what the claim forbids. A flag set is not a gate.

**4. Platform contract.** Read the platform's own docs for timing limits, retry behaviour,
token lifetimes and payload caps — then check your code against them, not against your memory.
This found a live-blocking defect (duplicate incident channels from a slow ack) that no test
could see.

**5. Restart and two-replica behaviour.** For every counter, cache and ledger: what happens on
restart, and what happens when a blue/green deploy runs two instances at once? Check id
generation and any scheduled job in particular.

**6. Real database.** Run the actual migrations against pg-mem or a real Postgres. Foreign keys,
NOT NULL columns and ON CONFLICT semantics are where hand-written fakes lie to you.

**7. Artifact accuracy.** Does the README describe the current directories? Does every route in
the manifest exist? Does the runbook's rollback claim survive a restart? These are read by
reviewers before anything else.

**8a. Boot smoke, from the built artifact.** `npm ci --omit=dev && npm run build && npm start`
on a clean checkout. Not the sources through ts-node — the thing you would deploy. This found
that the package had no runtime dependencies at all: `pg` and `ts-node` were both dev-only, so
a production install could not have started the service. Fifteen seconds, and it is the single
highest-yield check in this document after check 0.

**8b. Read your own test assertions for shape-instead-of-value.** When a test asserts a status
code, a length or a type rather than the value that belongs there, ask what value belongs
there. An assertion of `202` and an empty body is not a passing test; it is a description of a
response that never arrived.

**8. Adversarial pass.** Forge a signature, replay a request, pass another tenant's id, call an
admin route as a member, submit junk. Roughly 18 cases; it found a 500-instead-of-400 that would
have paged someone on malformed input.

**9. Which method does the deployed composition call? (v3)** For every enforcement,
persistence or claim method, write ONE test that builds the production composition (not a
service in isolation) and asserts the enforced outcome: declare `limit` then `limit+1`, claim
ids from two replicas, rotate a key and read the record back. Coverage of both methods proves
nothing about which one is wired. `audit.mjs` A10 finds the candidates mechanically; the test
is the judgement.

**10. Can a real adapter satisfy this contract? (v3)** Open every interface a platform
adapter must implement. If a method returns a value rather than a Promise, only a stub can
implement it, and every test above it is testing the stub. Convert the boundary *before* the
adapter sprint, budget every platform call, and add a floating-promise rule — the temptation
under deadline pressure is to fire-and-forget inside the sync function, which is exactly the
class the first review found (CF-007). `audit.mjs` A13 flags the interfaces.

**11. The gate must also permit. (v3)** A gate that only ever refuses has never been shown to
work. Build a fully-faked-but-healthy composition and assert it PASSES production; then rename
one fake to look real, make its `healthcheck()` fail, and assert it is refused *by the probe*.
A name is a claim; a round-trip is evidence. And make the provider set closed — typed to
exactly the required keys — so omission is a compile error rather than a review finding.

**12. Every queue has a lifecycle. (v3)** For every in-memory array or map that holds work
(not cache): is it registered with the shutdown path, and is it persisted if a `kill -9` must
be survivable? `audit.mjs` A12 lists the candidates; check the replay and retry queues in
particular, because they are added during fixes and forgotten.

## Suggested order across the portfolio

Risk-first, because these classes hide the most damaging defects:

0. **Gate coverage of the composition root** (check 0 + `audit.mjs` A8/A9) — two minutes, and
   until it passes, nothing else you measure means what you think it means. This is now first
   for the same reason a green suite over an unbuildable runtime is worse than no suite: it
   creates confidence that is exactly inverted.
1. **Promise tracing** (check 3) — it is the shortest check and catches the ones with customer
   or legal consequences: retention, encryption, billing limits.
2. **Caller audit** (`audit.mjs` A1 + check 1) — mechanical, and it found the single largest
   problem in OnCall.
3. **Real database** (check 6) — fifteen minutes, and it found a critical foreign-key defect.
4. **Restart and replica** (check 5) — only matters if you deploy, which you will.
5. **Enforcement wiring** (check 9 + `audit.mjs` A10) — the highest-yield v3 check; it found
   a blocker in the review and a 13th defect in the remediation.
6. **Contract shape** (check 10 + A13) — before ANY adapter sprint, or the sprint becomes a
   core-contract migration discovered mid-way.
7. The rest as time allows.

## Honest notes on the tool

- It flags patterns, and some flags are correct-by-design. Run against OnCall Copilot after all
  39 fixes it still reports 4 areas: two genuine build-time libraries, in-memory state that is
  deliberate behind adapters, and five *optional* collaborators that are optional so tests can
  omit them but are required in practice at boot. That is the intended behaviour — it tells you
  where to look, and you decide.
- It cannot see contract mismatches with a platform, missing surfaces, or a promise phrased in
  words it does not match. Those need checks 1, 3 and 4.
- A clean run means nothing on its own. Every one of the 59 defects coexisted with a green suite.
- Two of the checks report their own sibling modules. Run against OnCall Copilot v0.36.0, A1
  flags `src/composition/production.ts` and `src/http/session.ts` as uncalled, because their
  only importer is the composition root, which the tool classes as an entry point. That is
  correct-by-design and worth knowing: the tool cannot see through an entry point, which is
  the same blind spot the gates had.
- **Self-review has a floor, and this was it.** Twenty-eight internal releases, four
  self-review passes, a 100% coverage gate, a real-Postgres suite, an adversarial suite and a
  load run — and the first external reviewer still found ten blockers in ninety minutes.
  Treat an independent pass as a release input, not a launch formality.
- **A second independent reviewer finds the next layer down.** The Perplexity review did not
  re-audit CF-001..020; it found what a green gate over the *fixed* core still hid. Two
  reviewers from different vendors found different classes. Budget for a third (S50).
- **Run the tool against the remediation, not only the original.** v3 run against V037 found
  PX-013 (A10). The fix for one instance of a class rarely fixes the class.
- **v3 false positives to expect:** A11 will name the inventory function's own `providers`
  parameter unless the composition files are excluded (they are); A12 will name a `RecordingNotifier`
  and an error class with a `private failed = []` field — read the class name before acting.
