ShiftDesk for Microsoft Teams — what it is, what is finished, and what is not

A frontline shift-handover product that produces evidence an auditor can read. The code is finished and verified three ways. It has never run in a real Microsoft tenant, and nobody has bought it. Both of those sentences are true at the same time, and this page is about keeping them that way.

What the product does

A supervisor ending a shift writes a handover in Teams: what happened, what is outstanding, what the next shift must watch. The incoming supervisor acknowledges it, and that acknowledgement is the record. Around that core sit approval workflows with thresholds and blocked categories, digital checklists, kudos, and a manager dashboard over all of it. It installs as a Teams app with tabs and a bot, signs people in with their existing Microsoft identity, and keeps tenant data in PostgreSQL.

The reason to build it at all is narrower than the feature list suggests. Microsoft already gives every customer Approvals and Planner task publishing at no extra cost, so two of the three original pillars compete with free. What those tools do not produce is a retained, queryable handover record with an audit trail — the thing somebody has to find when an inspector asks about the night of the fourteenth. That is the wedge, and the positioning was rewritten onto it after an independent reviewer pointed out that the old framing competed with zero.

How a request actually moves through it

Two things in that picture are worth pausing on, because they are where this product has historically gone wrong. The first is the dashed vertical line. Until three days ago the production configuration had no working verifier on either side of it: tab sign-on accepted a hardcoded development string, and the bot's production authentication function returned false for everything, which meant the primary surface was inert in any real deployment. Both are now real verifiers with real signature checks, and the process refuses to start if a development shortcut is wired in outside development.

The second is the box on the far right. The same review found that DATABASE_URL was honoured nowhere — no database client was ever constructed, so the shipped server always ran from memory, and every claim about durability, encryption at rest, audit retention and data deletion rested on a store that evaporated on restart. That is now wired, with migrations on boot, and proven against a real PostgreSQL 16 rather than a test double. Within an hour of a real database being in the loop it exposed a defect that five releases of a fake store had never shown: the driver parses JSONB into objects while the code had been parsing it as text.

What is complete — and what the claim rests on

Complete here means one specific thing: the behaviour is pinned by a named test that fails if the behaviour changes. The gate has three tiers, which is itself a consequence of the review. A single hundred-per-cent coverage gate had coexisted with three critical defects, because coverage measures the execution of the code that exists and says nothing about whether the code that matters exists at all.

The number, stated plainly. 68 unit suites and 555 tests at 100% of statements, branches, functions and lines with no exemptions; 9 of 9 integration tests against a real database; a production-seam assertion that fails the build if any seam has no real implementation, and that runs again at boot so a mis-wired deployment refuses to serve rather than serving insecurely.

And the honest caveat that belongs next to it: this project has twice shipped a release where the gate was green and the gate itself was broken. The last one was found this week — the build never produced the tab page, so a clean checkout would have served a blank tab, and the test job never built before testing, so five suites were checking a tree no deployment would ever have. Both are fixed and both are now pinned. A green gate is necessary here and has never once been sufficient.

What is not complete, and why

Eleven items are open, and it is worth being precise about the reason, because none of them is open for lack of effort. Every one needs something that cannot be written: an access grant, a purchase, a person's time, or a customer's signature.

What stands between here and the finish line

The commercial picture deserves the same candour as the technical one. On the original per-seat assumptions the model never reaches break-even inside eighteen months, and the funding requirement is now stated outright in the financial model rather than left for a reader to infer. Per-site pricing changes that arithmetic, but not the evidence underneath it: both scenarios rest on a conversion rate and a price that no customer has yet paid. The number worth acting on is the funding requirement, and the thing that would replace these inputs with facts is the fifteen conversations.

How to read the colours

The three-way encoding is deliberate and it is the same in both figures and in every workbook in this set. Green means the behaviour is pinned by a named test. Amber means the code is finished and the proof needs something real — a tenant, a vault, an offer. Red dashes mean a person owns it, and no amount of code closes it. A decision in the tracker keeps those eleven red items on the board with their full estimates rather than quietly restating them as something greener, so the remaining work always reads honestly.
