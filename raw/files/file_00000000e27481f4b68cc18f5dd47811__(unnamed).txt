# 4. Detailed findings

## F01 — BLOCKER  
## Durable schema validation accepts hostile target-owned SQLite objects and can silently lose writes

V036 says it validates the “complete expected schema” derived from each store’s schema script. The implementation does not capture or compare the complete SQLite semantics.

### Root cause

`at_durable._fingerprint()` records only:

- Tables: column name, declared type, `NOT NULL`, primary-key position; and limited foreign-key table/from/to fields.
- Indexes: owning table and indexed column names.
- Triggers: trigger name and owning table.

It omits, among other things:

- Column defaults.
- `UNIQUE`, `CHECK`, generated-column, `STRICT`, and `WITHOUT ROWID` semantics.
- Foreign-key update/delete/match/deferred actions.
- Index uniqueness, origin, partial predicate, collation, sort direction, and expression details.
- Trigger timing, event, condition, and body.

`schema_differences()` then checks only that each expected named object exists with the limited recorded shape and explicitly ignores objects beyond the expected set because a sibling store may share the file. That makes an unexpected index or trigger attached to a **target-owned table** invisible.

### Independent adversarial reproductions

#### A. Unexpected unique index on an event-store table

A valid event database was modified with an additional unique index over event source fields. V036 reopened it successfully. Inserting two legitimate events from the same source then failed:

```text
IntegrityError: UNIQUE constraint failed:
event.workspace_ref, event.source_id, event.source_sha256, event.origin_kind
```

The transaction left `event_count = 0`.

#### B. Unexpected deletion trigger on an event-store table

A trigger was attached to the `event` table that deletes each inserted event. V036 reopened the database successfully. The API reported:

```text
reported_added = 1
```

But the database contained:

```text
event_count = 0
get_event(...) = None
```

This is silent durable-data loss: the store reports success for a record that does not exist.

#### C. Expected index name and columns, wrong uniqueness

An expected index was recreated with the same name and columns but as `UNIQUE`. V036 accepted the database because index uniqueness is absent from the fingerprint.

#### D. Wrong column default

A schema was created with `author_match DEFAULT 999`. V036 accepted it because defaults are absent from the fingerprint.

### Required V037 correction

- Define target-store ownership for every table and every object attached to those tables.
- Reject any unexpected index or trigger attached to a target-owned table. Sibling-store tolerance must apply only to genuinely sibling-owned objects.
- Build a full semantic fingerprint using, at minimum:
  - `PRAGMA table_xinfo` plus normalized table SQL for defaults, checks, generated columns, table constraints, `STRICT`, and `WITHOUT ROWID`.
  - Full `PRAGMA foreign_key_list` semantics, including update/delete/match and deferred behaviour where represented.
  - `PRAGMA index_list` and `PRAGMA index_xinfo` for uniqueness, origin, partial status, expression/collation/order/key columns, plus normalized partial predicates.
  - Full normalized trigger SQL, not only trigger name/table.
- Compare the exact set of target-owned objects and their complete semantics.
- Add permanent regressions for all four reproductions above.
- Every rejected open must leave the database and WAL/SHM/journal sidecars byte-identical.

## F02 — BLOCKER  
## The “single complete final seal” omits required gates and does not carry complete evidence

The sealer’s documentation says the complete test and audit sequence is non-skippable and that `seal_evidence.json` records every command, exit code, count, timestamp, and hash. The implementation and supplied seal record do not support those statements.

### Commands omitted by `tools/final_seal.py`

The pre-package `_gates()` runs:

- Deterministic pytest.
- Three generators.
- A second generator run.
- Validation of an already-existing `mutation_report.json`.

It does **not** execute:

- `python -m pytest tests/internal/integration -q -o addopts="" -m integration`
- Ruff.
- Mypy strict.
- `python tools/standalone_install_check.py`
- `python tools/mutation_regression.py`

The extracted-package `_reverify()` runs only deterministic pytest, each generator once, the package audit, CRC, and manifest verification. It does not rerun the integration, Ruff, mypy, standalone-install, or mutation gates against extracted bytes.

### Seal-record evidence

The separate V036 seal record contains no positive integration, Ruff, mypy, or standalone-install step. Its mutation entry contains only `killed` and `mutants`; it has no command, exit code, timestamp, report hash, or source-hash set. Therefore it does not satisfy the release’s own statement that every command, exit code, count, timestamp, and hash is recorded.

### Unbound sidecar

The README states that `seal_evidence.json` is “in this package.” It is not one of the 11 manifest-managed payloads in the outer ZIP. It was supplied as a separate sidecar and is not hash-pinned by the product manifest. The sidecar does hash the outer ZIP, but the delivery has no higher-level immutable envelope that pins both files together.

### Required V037 correction

- Put every required release command in one canonical gate registry and have the sealer execute it, rather than relying on prose or prior manual execution.
- Record for every gate: exact command, tool version, cwd, start/end timestamps, exit code, stdout/stderr digest or retained log, result counts, and relevant source/report hashes.
- Execute the required extracted-byte sequence against the exact packaged repository.
- Run the mutation command in the seal workflow, or explicitly produce a cryptographically pinned prior mutation execution record with its exact command, exit code, timestamp, report SHA-256, and source-hash set; do not represent a two-number summary as full command evidence.
- Record any legitimate integration skip and bind it to immutable authoritative CI evidence rather than silently omitting the gate.
- Resolve the sidecar circularity explicitly:
  - Include a manifest-pinned `seal_run_evidence.json` inside the product package that contains the command evidence but not the outer ZIP’s self-hash.
  - Produce an external `delivery_attestation.json` after packaging that hashes both the final product ZIP and the run-evidence identity.
  - Deliver both through one named delivery envelope or signed attestation so neither can be substituted independently.

## F03 — BLOCKER  
## `sealed_at` is captured before packaging and re-verification, not at the actual final seal

`tools/final_seal.py` assigns `sealed_at` immediately after the initial `_gates()` call. After that timestamp, it still:

1. Edits `tools/release_facts.py`.
2. Rebuilds release facts.
3. Regenerates facts blocks.
4. Reruns the deterministic suite.
5. Generates outer artefacts.
6. Builds the nested repository ZIP, manifest, and outer ZIP.
7. Re-extracts and tests the final bytes.
8. Runs the package audit.
9. Verifies CRC and manifest.
10. Writes the seal evidence.

The supplied record declares:

```text
sealed_at = 2026-08-11T18:23:05+01:00
```

Its last timestamped step is the extracted package audit at:

```text
2026-08-11T18:24:58.365014+01:00
```

That is approximately **113 seconds after** the declared seal. The 18:23:05 value is a build/release-stamp creation time, not a final-seal completion time.

### Required V037 correction

- Rename the current value to `release_stamp_created_at` or `build_started_at`.
- Record `seal_completed_at` only after the final extracted-byte audit, CRC/manifest verification, and evidence assembly have succeeded.
- Do not claim that an earlier stamp is the “actual final seal.”
- If the final filename must use the completion minute, rename the already-verified immutable ZIP after completion; renaming does not change its bytes. Keep internal build-stamp semantics distinct from completion semantics.
- Put the final outer SHA-256 and completion timestamp in the external delivery attestation described in F02.

## F04 — HIGH  
## The canonical release-facts audit accepts missing and extra derived fields

The current reader validates the `release-facts/1` wrapper, then iterates freshly derived facts and compares a value only when the key also exists in the shipped facts:

```python
for key, value in fresh.items():
    if key in shipped and shipped[key] != value:
        ...
```

It never requires exact key-set equality and never rejects extra fields.

### Independent diagnostic

A copy of the exact nested repository facts was changed as follows:

- Removed required field `tests_passed` whose shipped value is 670.
- Added `bogus_unverified_fact = 999999`.
- Preserved `schema = release-facts/1` and `integrity_failures = []`.

The exact V036 `audit_package()` returned:

```text
findings = 0
```

A canonical schema that accepts missing required fields and arbitrary extra fields is not canonical.

### Required V037 correction

- Require `set(shipped) == set(fresh)`.
- Report every missing and every unexpected key.
- Require type equality as well as value equality, avoiding Python equality aliases such as `True == 1` and `670.0 == 670`.
- Define any intentionally optional fields in an explicit schema rather than silently tolerating absence.
- Add negative regressions for missing required field, extra field, wrong type with equal value, malformed wrapper, and non-empty integrity failures.

## F05 — HIGH  
## Generator steps are labelled “zero-diff” without performing a diff or hash comparison

The sealer executes `git status --porcelain` but discards the result with `del diff`. It then labels a second generator run `*-second-run-zero-diff` solely because the generator exits zero. On extracted bytes, it runs each generator once and labels the run `*-zero-diff` without comparing any file before and after.

A successful generator exit does not prove that it changed no files. A second successful run proves neither that the first run was clean nor that outputs are deterministic unless the owned output bytes are compared.

### Required V037 correction

- Define the exact files owned by each generator.
- Hash those files before and after every generator run.
- Fail if the first release-validation run changes a generated artefact that was supposed to be current.
- Run again and require identical hashes.
- Repeat the before/after hash comparison on the extracted repository.
- Record the owned file set, before hashes, after hashes, and changed-file list in seal evidence.
- Remove “zero-diff” labels unless a real comparison returned no changes.

## F06 — MEDIUM  
## The current V036 review-disposition worksheet is still clipped, and its readability gate certifies it

The current sheet `29_V036ReviewDisposition` was rendered from the shipped workbook. The final F09 row is vertically clipped; the stored cell text continues beyond what the rendered row displays.

The readability function’s docstring says current sheets must declare usable widths, wrap cells, and render without manual repair. The implementation checks only:

- A populated column width of at least 9.
- A frozen header row.

It does not check:

- Wrapped alignment.
- Explicit or calculated row height.
- Auto-filter presence.
- Rendered clipping.
- Whether all text is visible.

The “readable” test also creates long wrapped content without any row auto-fit requirement, so the exact class can pass while clipping remains. The package audit returned zero findings for the shipped clipped sheet.

### Required V037 correction

- Set explicit calculated row heights for every wrapped multi-line row; do not rely on Excel opening the file and auto-fitting it later.
- Audit wrap settings, row heights, auto-filter, freeze panes, and column widths.
- Add a negative regression containing a long final wrapped row that the present gate falsely passes.
- Render every current workbook sheet during release assembly and retain preview evidence for the current review-disposition sheet.
- Fail the build when the rendered current governance sheet hides any text.

## F07 — MEDIUM  
## Identity compatibility claims are false, and current metadata contains an unresolved template token

V035 accepted and derived an `atid/3` identity for an aware year-1 instant. V036 rejects that same value before derivation. The V036 design choice to reject years before 1000 was allowed by the V035 review as an alternative to a scheme bump; the implementation is reasonable. The release wording is not.

Current files repeatedly claim:

> Every id derivable under V035’s atid/3 is byte-identical under V036’s.

That is false because some IDs derivable under V035 are no longer derivable under V036. The accurate statement is:

> For values accepted by V036, the canonical bytes and IDs remain unchanged from V035; V035-only aware instants before year 1000 are now rejected.

The current metadata also contains the unresolved literal:

```text
No accepted release ever wrote an id from a value {V} rejects
```

### Required V037 correction

- Replace the overbroad compatibility statement everywhere: README, metadata, changelog, ADR, `identity.toml`, code comments/docstrings, and project memory.
- State explicitly that V035 could derive pre-year-1000 identities while V036/V037 reject them.
- Support any assertion that no durable baseline actually contains those values with evidence; otherwise phrase it as an assumption or migration precondition.
- Remove the `{V}` token.
- Add a current-artefact audit for unresolved template placeholders such as `{STAMP}`, `{V}`, `TODO_REPLACE`, and equivalent markers.
