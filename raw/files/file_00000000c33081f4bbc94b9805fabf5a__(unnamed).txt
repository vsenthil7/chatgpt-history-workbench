# 09/08/2026 21:56 — 00003-AT-WP V013 Deep Review

## Review status

**Release verdict: REJECT / NO FREEZE / V014 hardening required.**

V013 is a materially stronger package than V012 and its official release evidence is internally substantial. The ordinary `run → joined read → guarded mutator` leak addressed by ADR-026 is closed. However, independent adversarial execution found three release-blocking defects that the 181-test, 100%-coverage, 97/97-mutation result does not exercise:

1. every in-memory store still exposes an unguarded full-state `restore()` mutation channel, including from READ frames;
2. several public work-object commands are split into separate read and write transactions, and `block()` can persist a stale interrupted state after a valid interleaving commit;
3. a raw string `"CRITICAL"` bypasses the critical-evidence completion policy.

A fourth high-severity rollback gap allows writes to survive a `BaseException`. The RTM currently labels the contradicted behaviours `ENFORCED`, so this is both an implementation defect and an evidence/governance defect.

# Findings

## F01 — BLOCKER: public `restore()` bypasses READ mode and transaction scope

### Evidence

Ordinary mutators call `_require_mutation_context()` in:

- `platform/packages/aumnity_kernel/src/aumnity_kernel/adapters/memory.py:61-89`.

The full-state restore methods do not:

- organisation restore: `memory.py:232-235`;
- principal restore: `memory.py:255-257`;
- work-object restore: `memory.py:369-370`;
- evidence restore: `memory.py:395-396`;
- audit restore: `memory.py:422-423`.

`InMemoryUnitOfWork.read()` correctly pushes a READ frame at `memory.py:502-525`, but a callback can call one of these restore methods directly and replace persisted state because restore never checks the current frame.

### Executed reproduction

```text
P1_JOINED_READ_RESTORE_MUTATION_PERSISTED True
P1_TOP_LEVEL_READ_RESTORE_MUTATION_PERSISTED True
```

Both a top-level READ and a READ joined into a WRITE transaction persisted a new organisation.

### Impact

This defeats the central V013 guarantee that read-only is context-independent. It also bypasses current-scope coverage: a nested narrow transaction can replace an undeclared ancestor store even though it holds no savepoint for that store. The same channel can wipe or inject organisations, principals, work objects, evidence, or audit events.

It contradicts:

- `RD-003` read-only in every context;
- `TXN-004` every mutation mechanically participates;
- `TXN-007` current declared scope is the mutation boundary;
- ADR-026's stated closure of the V012 leak.

### Required correction

Make restore transaction-internal or require current WRITE mode and current-scope coverage on every restore path. Preserve legitimate rollback through private/capability-based transaction plumbing or a correctly guarded internal protocol. Add the same negative matrix for all five stores: outside transaction, top-level READ, joined READ, undeclared nested WRITE scope, and caught nested failure. Also prove top-level and savepoint rollback still works.

## F02 — BLOCKER: public commands are split across transactions; `block()` persists stale state

### Evidence

`WorkObjectRegistry._transition()` correctly performs load, transition validation, mutation, persistence, and audit in one write transaction at:

- `platform/packages/aumnity_kernel/src/aumnity_kernel/workobject/service.py:403-428`.

But these public operations perform an earlier read/validation outside that transaction:

- `assign`: assignee membership at `service.py:248-262`;
- `resume`: `get()`/precondition at `service.py:270-274`;
- `block`: `get()`/precondition at `service.py:276-285`;
- `unblock`: `get()`/target selection at `service.py:287-297`;
- `restart_after_rework`: `get()`/precondition at `service.py:314-320`.

`block()` captures `work_object.state` from the completed read transaction and later writes it into `blocked_from` inside a different transaction. `READY` and `ASSIGNABLE` are both valid blockable states (`workobject/state.py:38-45`), so an intervening valid transition does not necessarily cause the later write to fail.

### Executed reproduction

The probe inserted a valid `mark_assignable` commit after `block()`'s read had returned but before `_transition()` acquired the write transaction:

```text
P2_STATE_AT_WRITE_WAS_ASSIGNABLE True
P2_STALE_BLOCKED_FROM READY
P2_EXPECTED_BLOCKED_FROM ASSIGNABLE
```

The aggregate was blocked from its current `ASSIGNABLE` state, but persisted `blocked_from=READY`. A later unblock therefore returns it to the wrong state.

### Impact

This is deterministic TOCTOU state corruption, not a theoretical race. It directly contradicts ADR-023 and RTM `RD-001`, which say every public operation is one transaction with no validate-to-write window.

### Required correction

Each public mutating operation must define one write command callback containing all binding, membership checks, aggregate loads, operation-specific preconditions, state derivation, persistence, and audit. `block()` must derive `blocked_from` from the aggregate loaded inside that write. Add deterministic interleaving tests for all five split operations and a machine-maintained inventory covering every public mutating method.

## F03 — BLOCKER: raw enum value bypasses critical evidence policy

### Evidence

`WorkObject` declares enum-typed fields, but `__post_init__` validates identifiers and version only:

- `platform/packages/aumnity_kernel/src/aumnity_kernel/workobject/model.py:38-71`.

`WorkObjectRegistry.create()` passes caller values directly into the aggregate:

- `service.py:184-238`.

The policy checks enum identity:

- `platform/packages/aumnity_kernel/src/aumnity_kernel/policy.py:28-36`.

Therefore `risk_level="CRITICAL"` remains a plain string and does not satisfy `risk_level is RiskLevel.CRITICAL`.

### Executed reproduction

```text
P3_RAW_CRITICAL_TYPE str 'CRITICAL'
P3_CRITICAL_COMPLETED_WITHOUT_EVIDENCE True
```

A work object carrying the externally visible value `CRITICAL` was advanced through approval and completed with zero evidence.

### Impact

The baseline's most important completion guard—no critical work completes without evidence—is bypassable through a public service argument despite static type annotations. This also reveals a broader defective-adapter/domain-boundary problem for `Priority`, `WorkObjectState`, `PrincipalKind`, and `EvidenceKind`.

### Required correction

Enforce canonical runtime enum types at public/domain boundaries and reject malformed adapter-returned aggregates before disclosure or action. Use fail-closed policy logic. Add raw-string, foreign-enum, and malformed-adapter regressions. Static typing is not a runtime trust boundary.

## F04 — HIGH: transaction rollback does not catch `BaseException`

### Evidence

Rollback catches `Exception` rather than `BaseException` in:

- joined tenant provisioning: `memory.py:309-315`;
- top-level tenant provisioning: `memory.py:323-329`;
- joined unit of work: `memory.py:481-487`;
- top-level unit of work: `memory.py:492-498`.

The surrounding `finally` releases the scope/lock, so a direct `BaseException` exits without restoration.

### Executed reproduction

```text
P4_BASEEXCEPTION_WRITE_PERSISTED True
```

A custom transaction-abort class derived directly from `BaseException` was re-raised, but the organisation written before the abort remained committed.

### Impact

Cancellation-style failures, `KeyboardInterrupt`, `SystemExit`, custom abort signals, and exception groups outside `Exception` can violate all-or-nothing semantics. This contradicts the implementation documentation's “ANY failure” wording at `memory.py:264-269` and `memory.py:433-435`.

### Required correction

Rollback on `BaseException`, restore before re-raising the exact original object, and add top-level/joined/provisioning/caught-nested regressions. Document intended cancellation semantics explicitly.

## F05 — HIGH: RTM claims `ENFORCED` for behaviour disproved by execution

### Evidence

The following rows are marked `ENFORCED` in `06-traceability/RTM.md:44-49`:

- `TXN-004`: every mutation mechanically participates;
- `TXN-007`: current scope is the mutation boundary;
- `RD-001`: every public operation is one transaction;
- `RD-003`: read-only is context-independent.

F01 and F02 disprove those broad claims.

G09's implementation checks only that a cited pytest node is collectable or an evidence/script file exists:

- `platform/scripts/gates/g09_rtm_gate.py:43-65` and `68-120`.

It does not enumerate public operations, adapter mutation methods, or semantics. A collectable test for one guarded mutator is therefore accepted as proof of “every mutation.”

### Impact

The gate converts partial evidence into a stronger enforcement claim than the suite establishes. This is why all official gates can pass while core RTM guarantees are false.

### Required correction

Temporarily downgrade affected RTM rows until closed. Add a machine-readable inventory of every published operation and adapter mutation primitive, with explicit positive/negative tests per path. Make G09 validate inventory completeness, not merely node existence.

## F10 — MEDIUM: `content_sha256` accepts values that are not SHA-256

### Evidence

`EvidenceRecord.__post_init__` calls only `require_identifier`:

- `platform/packages/aumnity_kernel/src/aumnity_kernel/evidence.py:29-57`.

Executed probe:

```text
SHORT_SHA_ACCEPTED abc
```

The field and docstring say the value fixes the artefact content, but no 64-hex validation occurs.

### Impact

A record can satisfy the critical-work evidence presence policy while carrying malformed checksum metadata. This does not prove the referenced content itself; it does not even prove the field is syntactically a SHA-256 digest.

### Required correction

Require exactly 64 hexadecimal characters and choose a normalised case, or rename/document the field as an opaque checksum. State separately whether URI resolution and content re-hashing are deferred.

## F11 — LOW: “bare critical section accepts no joins” is false for READ joins

### Evidence

`TransactionMutex.__enter__` says the empty bare scope accepts no coordinator joins (`memory.py:202-207`), and RTM `TXN-007` repeats that claim. But `UnitOfWork.read()` pushes an empty READ frame (`memory.py:515-520`), and the empty declared set is a subset of the bare frame's empty set.

Executed probe:

```text
BARE_SECTION_READ_JOIN_ACCEPTED joined
```

The existing `test_bare_critical_section_accepts_no_coordinator_join` tests only a WRITE UoW (`test_tenant_isolation.py:1929-1939`).

### Impact

No mutation authority is granted, so this is not a confidentiality/integrity bypass. It is a precise ADR/RTM/test overstatement.

### Required correction

Either reject all joins using an explicit bare-frame type, or document and test the actual rule: no WRITE joins, but READ joins are permitted and remain read-only.

## F12 — LOW: provider/domain validation and ADR ordering hygiene

`Clock.now()` promises an aware UTC datetime (`aumnity_contracts/providers.py:12-17`), but `TickingClock` accepts a naive `start` and zero/negative `step_seconds` (`providers.py:28-38`). That can produce naive or non-monotonic audit timestamps. Validate the constructor or deliberately weaken the contract.

The ADR index lists `ADR-020` after `ADR-026` (`12-adr/ADR-INDEX.md:24-30`). This is harmless to execution but should be corrected because the table presents itself as the canonical decision index.
