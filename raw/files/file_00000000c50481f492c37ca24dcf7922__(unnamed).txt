### R-04 --- WP-10 is not build-ready as specified

Claude defines WP-10 as:

> "limiter wired; configurable"

and proposes D2 → D3.

But FR-080 requires:

-   Redis token bucket;
-   100 req/min authenticated;
-   20 req/min unauthenticated;
-   per-tenant-per-user;
-   `Retry-After`;
-   health/metrics exemptions;
-   Flutter 429 handling/backoff;
-   admin behaviour.

The repository's current `RateLimitMiddleware` is an **in-process
fixed-window counter keyed only by client IP**, with a single default
limit of 100 and no `Retry-After`.

Simply wiring that implementation would turn an unwired non-conformant
design into a **wired non-conformant implementation**.

**Correction required:** WP-10 acceptance criteria must reproduce
FR-080, not merely "wire middleware."

**Coding impact:** blocks **WP-10**, not the whole corrected first
batch.

### R-08 --- E-02 proves less than the lifecycle wording sometimes implies

E-02 genuinely **executed** code. It imported the repository's
production canonicalisation/hash functions and proved that the existing
`content_hash` can structurally participate as a leaf in a larger hash
structure.

It did **not** execute:

-   RFC 4998 ASN.1 EvidenceRecord generation;
-   RFC 6283 XML;
-   an RFC3161 TSA transaction;
-   `openssl ts -verify`;
-   an actual reduced hash tree artefact;
-   timestamp renewal;
-   hash-tree renewal;
-   blockchain anchoring.

**Correction required:** use:

> **"Structural compatibility hypothesis successfully prototyped;
> standards-conformant ERS encoding and real RFC3161 verification remain
> unverified."**

There is a second architecture issue: an **offline verifier cannot prove
that a certificate is currently unrevoked** unless it has a sufficiently
fresh signed/anchored status artefact. It can prove status **as of the
latest status evidence it possesses**.

That distinction must appear in the lifecycle and CR-12.

### Why keep the AI messages as files?

The Git record should carry the decision/evidence chain. Chat history
should be treated as supporting working context, not as the only
authoritative record.

For every material Claude or ChatGPT review that changes the next
action, retain either:

1.  the complete AI-produced Markdown artifact; or
2.  a compact immutable decision/evidence record containing the
    prompt/input identity, verdict, findings, corrections, and resulting
    authority.

There is no need to save every conversational message. Save the
messages/artifacts that **create evidence, challenge evidence, recommend
a decision, record a PO decision, change a gate, or authorise work**.

This gives TalkProof a reconstructable chain:

**source → review → challenge → correction → decision → build → test →
evidence → gate**.
