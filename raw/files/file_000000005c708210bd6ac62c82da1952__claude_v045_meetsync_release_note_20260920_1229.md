### PR-01, because it was the one that mattered

`/oauth/start?account_id=<victim>` signed the victim's id into `state`; the callback installed whatever Zoom login completed OAuth onto that id and minted an **owner** session for it. Learn a workspace id, complete OAuth with your own Zoom account, and you held their export, their delete-my-data, their CRM queue — with their Zoom integration silently repointed at your grant.

The state signature was doing its job. It proved *the server issued this state*; it could not prove *the caller owns this account*. Every test supplied an `account_id` and asserted that the same account came back, so the suite asserted the vulnerability as intended behaviour — the VER-M01 shape again, tests agreeing with the code about a contract that reality defines.

Now: after the code exchange, `GET /users/me` with the token Zoom just issued decides the tenant. The query parameter is an attribution hint, refused with a 403 and an `install.tenant` audit row when it disagrees — no account row written, no session minted. `installAccount` re-checks the same invariant, so the store is the last place the class can be stopped. The rule is the first standing rule in `docs/THREAT_MODEL.md`: **tenant identity always comes from the platform, never from the caller.**

## What is now true that was not

The product loop closes without a human API call. A meeting ends, the transcript arrives, fields are derived, and — when a CRM is connected and mapped — they are staged on a review screen for an explicit Approve. Exactly one job per meeting, whatever Zoom redelivers. Review is **on** by default, because a writeback nobody looked at is the failure a RevOps buyer fears most.

The front end uses the back end. 48 typed client methods, every panel reading and writing through them with optimistic updates that roll back on refusal, and an RTL suite that drives a fake server and checks what it *received* rather than handing panels the props it then observes.

Sessions can end. Sixty minutes, a `jti`, a durable deny list and a per-account watermark; uninstall and delete-my-data revoke everything; delivery is an HttpOnly cookie, not a URL fragment that lands in browser history and the Zoom client's logs.

Claims are code. `src/claims.ts` is what `/trust` serves and what `docs/TRUST_PAGE.md` is checked against. PostHog, Sentry and Stripe are gone from the page because nothing sends them data. The help centre no longer says "two read scopes" where the map lists four.

## A note on the review programme

The reviewer's diagnosis is accepted, and it is the most useful thing in the document. Every pass from v013 to v044 asked "is this module correct?" or "what calls this?" — questions answerable from inside the repository. The findings clustered precisely where those questions cannot reach: whether the front end uses the back end, whether identity means anything, and whether the claims in the marketing artefacts are true. Rigour was applied inside the repository boundary while the claims that mattered lived outside it.

The answer is not more self-review. It is two more gates that fail the build — route→client and document→code — because a standing gate is the only form of vigilance that survives the sitting that wrote it.
