2. Context

What TeleField is. A Zoho CRM Marketplace extension for Indian SME sales floors. A rep opens a widget inside Zoho CRM; TeleField hands them the next lead to call, records the outcome and the disposition, schedules callbacks, plans the day's field visits (beats) with geo-verified check-ins, scores the team, and bills the tenant. It is built in TypeScript/Node with an Express HTTP surface, server-rendered screens and Postgres persistence.

Where the product sits. Three independent reviews have now been run against it. The first (internal, 17 cold passes, v013–v031) found 35 defects in code that already carried 100% test coverage. The second (ChatGPT, 14 Sep, against v031) returned BUILD, NOT LAUNCH with 10 findings and a 13-sprint order E01–E13. The third (Perplexity, 16 Sep, against v032) returned 8 further findings, downgraded two acceptance gates, added two more, and restructured the work into 14 sprints PX01–PX14. Release v033 executes every one of those sprints that can be finished without something from outside this environment.

The one fact that governs everything below. Every remaining piece of work needs an account, an org, a vendor or a customer. None of it is blocked on engineering effort. That is a scheduling problem in Senthil's calendar, not a backlog problem in the code — and it is why a product with 1,769 passing tests still cannot place a telephone call.

9. What is not complete, and why

Ordered by what it blocks. "Why not" is the real reason, not a euphemism for "not got to it yet".

MissingSprintWhy it is not builtWhat unblocks itConsequence today
Place a real phone call
LAUNCH BLOCKER		PX08 An adapter needs a provider sandbox to be written against. Writing one from published documentation alone produces code that is self-consistent and wrong about the platform — which is precisely what VER-T1, VER-T4 and VER-T5 cost this product three separate times. The seam, the error taxonomy and the compliance gate in front of it are all built; the adapter is deliberately not guessed. Two India provider sandbox accounts (Exotel / Ozonetel class) — Senthil, decision D18 The product records calls the rep places on their own handset. The listing's central promise is unmet.
Live install in a Zoho org
LAUNCH BLOCKER		PX07 Two platform assumptions (the CRM service name and the SDK URL) are isolated in one file and flagged as unverified. Install, uninstall, disable, enable and update webhook shapes, scope approval, Multi-DC behaviour and the marketplace validator all need a real org to exercise. Zoho developer account + Sigma project + dev org — Senthil, LC-1 Nobody has ever installed TeleField. A browser can still assert an org id; the server only checks that the org exists.
Live DLT / NCPR registerPX03 remainder Connecting to the register requires a registered vendor relationship. Everything local was built instead: the consent ledger, the registry, the suppression table, the freshness gate and the report. The manual path — export the batch, scrub on the portal, upload the response — is functional and honest, exactly as ManualProvider is for telephony. A register/DLT vendor account — Senthil Scrubbing is an operator task on a schedule rather than an automatic call. The gate still refuses to dial an unscrubbed number.
Notifications that reach a humanPX09 No email or SMS provider is connected, so noopEmailSender is wired into the production scheduler. Every dunning notice, SLA breach, error spike and scheduler failure is computed correctly and then discarded. An email/SMS provider account — Senthil Do not take money before this ships. A paying tenant whose card fails is never told, and neither is the operator.
Call recordingPX08 Recording is produced by the telephony provider; there is nothing to record without an adapter. The pieces it will need — consent basis with an evidence reference, per-attempt traceability, erasure parity for new datasets — were built in PX03 so it is not a retrofit. Rides PX08 The AI roadmap (PX14) has no input, and BFSI buyers cannot be answered on compliance recording.
Async DB-first repositoryPX05 2nd half The Store interface is synchronous and all 53 modules are built on it; making it async is a rewrite of every call site, not a sprint item. v033 took the half that could be taken safely — transactional batches and conflict detection — and stopped there rather than starting a rewrite it could not finish. Nothing external — scheduled Claude work Still single-writer: blue/green deploys must drain the old process first. A crash between a mutation and its flush loses that one in-flight request.
Mobile PWA + manager control towerPX10 Not blocked at all — simply outside this release's scope, which the review itself set at PX01–PX06. The server-side halves (offline sync API with dedupe, scorecards, metrics, funnels, SLOs) already exist. Nothing — say "go ahead" Field reps have no offline shell; managers have the numbers but not the two-minute drill-down.
Vernacular screens + vertical packPX11 Also unblocked and out of scope. The manifest declares en/hi/ta and the widget chrome is translated; the nine screens are English, which the code states honestly rather than pretending otherwise. Nothing — say "go ahead" "Vernacular" is a weak claim as sold. Three strings in Tamil is not a vernacular product.
SSO/SCIM, pen-test, DR proofPX12 An external penetration test needs a vendor engagement. The static controls are strong and scanned in CI, but nobody outside this build has ever attacked the product. Pen-test vendor — Senthil Enterprise procurement cannot be answered. Scope PX01's finding into the brief when it is written.
Evidence anyone wants it
HIGHEST VALUE		PX13 No design partner has ever used the product. This needs five conversations, not code — and the review is explicit that it should happen before PX08, because PX08 is the most expensive and least reversible sprint in the plan. 3–5 design partners, two in a DLT-heavy vertical — Senthil Zero users. The repositioning (P-D1) is a hypothesis with code behind it and no market evidence.
AI follow-up intelligencePX14 Correctly last: it depends on recordings (PX08) and on the pilot saying the workflow is wanted (PX13). Building it now would be building on two unvalidated assumptions. PX08 + PX13 None — this is the right thing to not have built.
The pattern worth naming. Nine of the eleven rows above are blocked by an account, an org, a vendor or a customer. The build loop has been optimising for artefacts that can be produced without external dependencies, and it has produced them to an unusually high standard. Every remaining gate needs something from outside. That is a sequencing problem in the calendar, not a backlog problem in the code.

11. Glossary

TermMeaning in this document
DLTDistributed Ledger Technology platform operated under TRAI rules, on which every commercial caller registers its entity, sender headers and content templates before running campaigns.
NCPRNational Customer Preference Register — the do-not-disturb register outbound lists must be scrubbed against before each campaign run.
140 / 1600 seriesNumber ranges mandated since 1 January 2026: 140 for promotional calls, 1600 for BFSI service calls.
SuppressionA block held against a phone number (not a lead record), so a re-imported contact stays blocked.
LeaseThe period a claimed lead is held for one rep before it returns to the queue.
Gate (review gate)A build-breaking check that catches a class of defect rather than one instance. Nine of them run as npm run gates.
Gate (acceptance gate)One of the twelve launch criteria in Figure 4. Unrelated to the above, and unfortunately both are called gates.
PX01–PX14The sprint numbering from the Perplexity review, mapped onto the earlier E01–E13 numbering from the ChatGPT review.
Done-in-codeBuilt and tested here, but with no live evidence. It is deliberately not called "done".
