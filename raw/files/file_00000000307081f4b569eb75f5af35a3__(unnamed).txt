# Detailed findings

## F48 — P1 BLOCKER: excluded-name payload bypass remains

### Evidence

`scripts/manifest_policy.py:31-45` defines excluded directory names and basenames. `is_managed()` at lines 48-52 excludes a path whenever **any component** matches an excluded directory or whenever the **basename** is one of the excluded files.

This means the attacker no longer chooses any dot-prefixed name, but can still choose one of the named exclusions:

- `.evil/PACKAGE-MANIFEST.json`
- `.evil/.coverage`
- `.evil/.DS_Store`
- `.git/hooks/post-checkout`

All four were added **after manifest generation**. The untouched manifest was then checked with the shipped release-mode validator. Every case returned:

```text
CONSISTENCY: PASS
```

The currently shipped baseline manifest has the same problem. I replaced:

```text
10-baseline/AUMNITY-Capacity-Governed-Work-Orchestration-v0.1.0/PACKAGE-MANIFEST.json
```

with `{"tampered": true}` while leaving the outer manifest unchanged. The validator still returned `CONSISTENCY: PASS` because every file named exactly `PACKAGE-MANIFEST.json` is ignored anywhere in the tree.

### Why this is material

The release claims that the manifest is closed over shipped files and that the excluded universe cannot be selected by an attacker. That is not yet true. A release archive can carry executable or misleading unmanifested content under a permitted exclusion name and still pass the gate.

### Required correction

1. In **release mode**, do not silently ignore dev/cache/VCS artifacts. Reject them if present.
2. Exclude the root manifest by **exact relative path** only: `Path('PACKAGE-MANIFEST.json')`.
3. Either include the baseline manifest in the outer manifest or validate it explicitly and bind its exact path/hash.
4. Separate `development-generation exclusions` from `release-validation policy`; release validation should be fail-closed over every regular shipped file except narrowly identified self-referential metadata.
5. Add regressions for every currently named exclusion at root and nested locations.

## F49 — P1 BLOCKER: file-kind/symlink and outer-ZIP envelope are not bound

### Evidence A — symlink substitution

`managed_files()` uses `path.is_file()` (`scripts/manifest_policy.py:55-63`), which follows symlinks. The validator then uses `p.is_file()`, `p.read_bytes()` and `p.stat()` (`scripts/validate_consistency.py:160-171`), which also follow symlinks. Neither the manifest nor validator records/checks file kind.

Independent reproduction:

1. Copy the original bytes of `src/cgwo_core/__init__.py` to the excluded path `.git/objects/payload`.
2. Replace `src/cgwo_core/__init__.py` with the symlink `../../.git/objects/payload`.
3. Do not modify the manifest.
4. Run the shipped consistency validator.

Result:

```text
CONSISTENCY: PASS
```

The complete 438-test suite also remained green because imports followed the link. Thus a manifest entry that originally denoted a regular source file can become a symlink without detection.

### Evidence B — outer ZIP sibling

No shipped script validates the ZIP envelope itself. `scripts/run_gates.sh:8-19` validates only the extracted repository. I appended an unmanifested sibling entry outside the canonical root:

```text
UNMANIFESTED-SIBLING-PAYLOAD.py
```

After extraction, the canonical root's validator returned `CONSISTENCY: PASS`; it cannot see sibling archive entries. The narrative `evidence/package-verification.txt` says unsafe paths/symlinks were checked, but the procedure is not shipped as an executable/re-runnable gate.

### Required correction

1. Use `lstat()`/non-following traversal and reject **every symlink or non-regular file** in release mode before hashing.
2. Record and verify file kind; optionally record executable/mode bits where relevant.
3. Add `scripts/verify_release_zip.py <zip>` that enforces:
   - exactly one canonical top-level root;
   - no absolute paths, `..`, NUL, duplicate names, case-fold/Unicode collisions;
   - no symlink/device/FIFO entries;
   - no entries outside the root;
   - archive regular-file set exactly matches the release manifest plus the narrowly allowed root manifest;
   - extracted files revalidate without following links.
4. Make the ZIP verifier part of the one-command release ladder and machine-generated evidence.

## F50 — P1 BLOCKER: authorization decision can fail open

### Evidence

`AuthorizationPort.is_entitled()` declares a `bool` return (`src/cgwo_core/authz.py:47-62`), but `assert_authorized()` at lines 121-142 does not enforce that runtime contract:

```python
if not authz.is_entitled(checked):
    ... deny ...
```

Independent probes against the shipped code:

| Port behaviour | Result |
|---|---|
| `is_entitled = True` as a non-callable attribute | `isinstance(..., AuthorizationPort)` is `True`; raw `TypeError: 'bool' object is not callable` |
| method returns `object()` | **authorization succeeds** because the object is truthy |
| method returns `[]` | controlled denial, but a non-bool is silently treated as policy |
| method returns object whose `__bool__` raises | raw `RuntimeError` |
| `is_entitled` property raises | raw `RuntimeError` during structural protocol check |
| method raises | raw provider exception |

### Why ADR-015 does not dispose of this finding

This is not an attempt to prove the provider is genuine or hostile-proof. The provider may remain trusted. The defect is that the domain does not enforce the **declared return contract** of its trusted port and can turn an adapter bug such as returning `'false'`, a response object, or another truthy value into authorization. That contradicts the package's own exact-type stance and its guarantee that it enforces an allow/deny decision.

### Required correction

1. Call the supplied decision function once inside a controlled boundary.
2. Require `type(decision) is bool` before branching.
3. Treat non-boolean decisions as a controlled, fail-closed authorization-contract error; never coerce truthiness.
4. Decide and document a controlled error for provider access/call failures.
5. Add adversarial tests for non-callable member, truthy/falsey non-bools, hostile `__bool__`, raising descriptor and raising call.
6. Ensure all protected operations receive the corrected behaviour through `assert_tenant_operation()`.

## F51 — P2: manifest schema contains unchecked metadata

### Evidence

The V011 test and release notes claim that the manifest schema carries no unverified/unvalidated fields:

- `tests/test_manifest_closure.py:147-150`
- `00-control/RELEASE-NOTES-V011.md:8`

The validator checks file path/hash/bytes, duplicates, `file_count`, release/root matching and closed-set membership. It does **not** validate the exact value/type/schema of at least:

- top-level `schema`;
- top-level `project`;
- `generated` timestamp format/type;
- exact top-level key set;
- exact per-entry key set and types.

I independently changed each of `schema`, `project` and `generated` to false values; each modified package returned `CONSISTENCY: PASS`. Unknown top-level and per-entry assertion fields also passed.

### Required correction

Use a strict manifest schema or equivalent manual validation: exact required keys, exact primitive types, path grammar, SHA-256 grammar, non-negative integer byte count, exact schema/project constants, timestamp format and an explicit unknown-key policy. If some metadata is intentionally informational, narrow the documentation claim to the fields actually verified.

## F53 — P2: wire-integer grammar and implementation disagree on leading zeros

### Evidence

`src/cgwo_core/contracts.py:47-65` defines the accepted wire grammar as `[0-9]+` and describes one semantic value bound shared by string and integer inputs. Lines 120-146 reject a string before decoding when its raw digit count exceeds the maximum value's digit count.

Therefore:

```text
parse_wire_int(1)                 -> 1
parse_wire_int('1')               -> 1
parse_wire_int('00000000000001')  -> INTEGER_OUT_OF_RANGE
```

The last value matches the declared grammar and semantically equals 1, but is rejected solely because of leading-zero representation length.

### Required correction

Choose one explicit contract:

- **Permit leading zeros:** strip leading zeros for the safe significant-digit check, then decode/bound by value; or
- **Canonicalise the grammar:** change it to `(?:0|[1-9][0-9]*)`, document that leading zeros are invalid, and return `INVALID_WIRE_INT` rather than `INTEGER_OUT_OF_RANGE`.

Add equivalence/property tests across exact-int and string representations.
