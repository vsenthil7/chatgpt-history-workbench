Partner, these four questions are **not random interview questions**.  
They are designed to reveal **how a student thinks**, not just whether they can write code.

Each question tests a **different layer of engineering thinking**.

---

# 1️⃣ “Why did you choose this approach?”

## What this question tests
This question tests **reasoning and decision making**.

The interviewer wants to know:

```text
Did the student understand the problem
OR
Did the student just write code that works?
```

---

## Why this question exists

In real software development there are **many ways to solve the same problem**.

Example problem:

```text
Find the largest number in an array
```

Possible approaches:

| Approach | Idea |
|---|---|
Loop | Check each element |
Sort array | Largest becomes last |
Divide and conquer | Recursion |

All give the same result.

But engineers must decide:

```text
Which approach is best?
```

---

## What a good answer looks like

Example response:

```text
I used a loop because it only requires one pass through the array.
Sorting would take more time since it rearranges the whole array.
```

This shows:

• reasoning  
• efficiency awareness  
• understanding of alternatives

---

## When this question matters most

It becomes critical in roles like:

- Software Developer  
- Backend Engineer  
- System Architect  

Because engineers constantly decide **between multiple design options**.

---

# 2️⃣ “What is the time complexity?”

## What this question tests

This question checks whether the student understands **performance**.

Computers can run code quickly for small inputs, but performance becomes critical when input grows.

---

## What time complexity means

Time complexity measures **how the running time grows with input size**.

Example:

If input size = `n`

| Complexity | Meaning |
|---|---|
O(n) | time grows linearly |
O(n²) | time grows much faster |
O(log n) | very efficient |

---

### Example

Array search:

```text
for i in array
    check element
```

If array has 1000 items → 1000 checks  
If array has 1 million items → 1 million checks

This is:

```text
O(n)
```

---

## Why interviewers ask this

Real systems often process:

- millions of users  
- billions of records  
- large data streams

A poor algorithm can cause:

```text
slow system
server overload
high cost
```

So engineers must think about **efficiency before writing code**.

---

# 3️⃣ “What happens if the input becomes very large?”

## What this question tests

This tests **scalability thinking**.

The interviewer wants to know:

```text
Can the student think beyond small examples?
```

---

### Example

Suppose a program processes:

```text
10 numbers
```

Almost any method works.

But what if the input becomes:

```text
10 million numbers
```

Problems appear:

- memory usage  
- processing time  
- system load

---

### Example scenario

Code:

```text
Sort entire dataset
```

For small input → fast  
For huge input → slow

A better solution may require:

- streaming processing  
- partial computation  
- different algorithm

---

### Real-world relevance

Large-scale companies handle huge data volumes.

Examples:

- search engines  
- banking systems  
- social media platforms  

Even simple algorithms must scale.

---

# 4️⃣ “Can you solve it in another way?”

## What this question tests

This tests **flexibility of thinking**.

The interviewer checks whether the student understands:

```text
the problem
OR
only the solution they wrote
```

---

### Example

Problem:

```text
Find duplicate numbers in a list
```

Possible approaches:

| Method | Idea |
|---|---|
Nested loops | Compare every pair |
Hash set | Track seen numbers |
Sorting | Detect adjacent duplicates |

Each has different:

- speed
- memory usage

---

### What a strong candidate does

A strong candidate might say:

```text
We could also use a hash set.
That would reduce comparisons and make the solution faster.
```

This shows:

• conceptual understanding  
• algorithm knowledge  
• ability to evaluate trade-offs

## Why this single prompt is better than two

Because this forces the architect page to think in **one connected enterprise system**:

```text
question bank
↓
delivery engine
↓
candidate session
↓
proctoring evidence
↓
submission capture
↓
coding/runtime evaluation
↓
AI inference
↓
human review
↓
audit
↓
analytics
↓
skill profile
```

That is the correct systems view.

If we had split it into:
- Prompt 1 = exam AI
- Prompt 2 = coding AI

then the architect may accidentally design:
- two audit systems
- two review systems
- two model governance flows
- two telemetry pipelines
- two analytics systems

That would be structurally weaker.
