# 🧩 Architecture

## 1. User Problem

Operational teams often receive messy, incomplete, unstructured inputs such as:

- incident reports
- support requests
- escalation notes
- internal issue descriptions
- compliance-sensitive action requests

Humans lose time in:

- reading
- categorizing
- deciding action
- checking policy
- escalating uncertainty
- documenting why a decision was made

The system solves this by giving:

- structured understanding
- recommended action
- confidence signal
- policy-aware check
- escalation trigger
- audit record

---

## 2. Primary User

Choose one primary user only for v1.

### Recommended user
**Internal operations / incident triage analyst**

Alternative lanes:
- support ops reviewer
- governance/compliance reviewer
- recruiting ops screener
- nonprofit operations coordinator

For strongest fit with your background, use:

> **incident / operations triage analyst**

---

## 3. Core Workflow

### Input
User submits:
- raw incident text
- category hints
- priority hint if any
- optional attached evidence/reference text

### AI Processing
System performs:
1. issue understanding
2. category detection
3. severity estimate
4. action recommendation
5. policy/rule check
6. confidence assessment
7. escalate-or-not decision
8. explanation generation
9. audit log creation

### Output
System returns:
- structured summary
- recommended next action
- rationale
- policy flags
- confidence level
- escalation status
- reviewer notes field
- trace entry

---

## 4. System Components

### A. Input Layer
Handles:
- form submission
- raw text ingestion
- optional metadata
- validation

### B. Orchestration Layer
Controls:
- prompt routing
- multi-step reasoning flow
- structured output generation
- failure handling

### C. Policy Layer
Checks response against explicit rules such as:
- do not auto-close certain issue classes
- escalate high-risk or ambiguous cases
- require evidence for certain recommendations
- block unsafe next-step actions
- force human review on policy-triggered conditions

### D. Confidence / Escalation Layer
If:
- confidence low
- ambiguity high
- policy trigger activated
- evidence missing
- unsafe recommendation risk

Then:
- do not finalize
- escalate to reviewer

### E. Audit / Trace Layer
Stores:
- input
- output
- policy result
- confidence result
- escalation decision
- timestamp
- prompt/version info

### F. UI Layer
Simple v1 interface:
- incident input box
- process button
- output panel
- policy flags panel
- escalation status
- decision history

### G. Eval Layer
Tests:
- correctness
- policy compliance
- escalation quality
- explanation usefulness
- failure cases
- regression stability

---

## 5. Suggested Technical Shape

Keep it simple.

### Frontend
- minimal web UI
- clean single-screen workflow

### Backend
- API layer for orchestration
- structured output validation
- logging
- eval runner

### Model Usage
Use LLM for:
- summarization
- classification
- action drafting
- explanation
- ambiguity detection

### Rule Engine
Use deterministic logic for:
- policy enforcement
- escalation thresholds
- blocking unsafe actions
- required evidence conditions

### Storage
Store:
- sample cases
- outputs
- audit trail
- eval results

---

## 6. Required Output Schema

Every response should follow a stable structure like this:

### Incident Analysis Output
- issue_summary
- issue_category
- severity_level
- recommended_action
- action_reasoning
- policy_flags
- confidence_score
- escalation_required
- escalation_reason
- evidence_used
- reviewer_notes
- audit_id

This is important because it makes the system look engineered, not improvised.

---

## 7. Policy Rules for v1

Keep rules small and visible.

### Example rules
- High severity + low confidence → escalate
- Missing evidence on critical action → escalate
- Sensitive/compliance category → human review mandatory
- Unsafe recommendation keywords → block output
- Ambiguous root cause → do not auto-finalize
- Low severity + high confidence + no policy flag → allow recommendation

This is enough to prove the pattern.

---

## 8. Eval Design

You need a small but credible eval suite.

### Golden Set
Create 30–50 realistic cases.

Include:
- easy cases
- medium ambiguity cases
- edge cases
- unsafe recommendation traps
- policy-sensitive cases
- incomplete information cases

### Measure
For each case track:
- category correctness
- severity quality
- action quality
- policy compliance
- escalation correctness
- explanation usefulness

### Failure Tags
Every failed case should be tagged with one or more:
- wrong classification
- wrong severity
- wrong recommendation
- missing evidence
- failed escalation
- overconfident output
- policy miss
- unclear explanation
