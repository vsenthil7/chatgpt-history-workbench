# 🔴 P0-1 — Tenant isolation can be bypassed

This is the most important finding.

`src/uraiflow/core/tenancy.py` trusts Python string behaviour:

```python
if ctx.tenant_id != tenant_id:
    raise TenantIsolationError(...)
```

`TenantContext.__post_init__()` similarly trusts `.strip()`.

A hostile `str` subclass can override comparison and make a foreign tenant compare equal.

I executed this directly against the shipped V004 code.

Conceptually:

```python
class EvilStr(str):
    def strip(self, *a, **k):
        return "x"

    def __eq__(self, other):
        return True

    def __ne__(self, other):
        return False
```

Then:

```python
ctx = TenantContext(EvilStr("tenant-A"), EvilStr("actor"))
require_same_tenant(ctx, "tenant-B", "secret")
```

### Actual V004 result

**No exception.**

I got:

> `TENANT_BYPASS: yes`

That means the supposedly enforced **SaaS-002 tenant boundary is bypassable**.

This is not merely a test omission. It is a **trust-model defect**.

## Step 2 — Understanding the V004 processing flow

The central UraiFlow workflow can be understood like this:

**Application/User → Operation Request → Validate → Prepare → Commit through adapters → Finalise**

If something goes wrong after partial work has already happened:

**Failure → Compensation → Rollback committed operations → Record recovery state**

If normal automatic compensation cannot completely recover:

**Recovery Service → authorised retry or manual resolution → audit evidence**

That is a sound overall architectural direction.

### 2A. Validation

The first responsibility is making sure the request is internally valid before UraiFlow touches an external system.

Conceptually it validates things such as:

- tenant context;
- actor/request context;
- records being processed;
- idempotency information;
- adapter information;
- operation-level invariants.

The goal is:

> **bad request → stop before side effects**

rather than:

> bad request → partially write external systems → discover the problem later.

## Step 3 — Prepare phase

After validation, UraiFlow prepares the records that will be committed.

Imagine an audio/transcription workflow eventually deciding:

> “This sentence means update employee X's timesheet and create another planner record.”

UraiFlow should determine the intended operations first.

Only after that should it start committing to external systems.

This gives the architecture a clean separation:

**decide first → execute second.**

That matters because an external system may succeed for record 1 and fail for record 2.

# Step 4 — Adapter architecture

UraiFlow does not directly hard-code every external system.

Instead, it communicates through adapters.

For example, eventually there could be adapters for:

- Google Sheets;
- CRM;
- HR system;
- planner;
- timesheet system;
- accounting system;
- another SaaS API.

V004 strengthened adapter identity by introducing a machine identity called `adapter_id`.

Earlier, human-friendly names could create ambiguity.

For example:

`TimesheetAdapter`

may be a display/name concept.

But machine orchestration needs something stronger, such as an immutable unique adapter identity.

So V004's principle is:

> **machine-to-machine decisions should use machine identity, not a friendly display name.**

That is correct.

# Step 5 — Commit receipt

This is one of the most important parts.

Suppose UraiFlow tells an external adapter:

> “Create this record.”

The adapter returns a **receipt**.

The receipt effectively says:

> “I committed operation X for tenant Y, record Z, under idempotency key K, and here is the resulting external identifier.”

V004 added validation of that receipt.

That is very important because UraiFlow must not blindly believe:

> “adapter returned something, therefore everything is correct.”

The orchestrator checks whether the returned information corresponds to what it actually asked the adapter to do.

So the architecture is moving toward:

**request → external operation → independently verify returned receipt → accept**

instead of:

**request → external operation → trust adapter response**

That is a substantial improvement.

# Step 6 — Why compensation exists

Imagine three external operations:

```text
A succeeds
B succeeds
C fails
```

You do not want the system to remain:

```text
A = committed
B = committed
C = missing
```

while internally pretending that the overall workflow failed cleanly.

V004 therefore has compensation logic.

Conceptually:

```text
commit A
commit B
commit C → failure

rollback B
rollback A
```

This tries to restore the external world to a consistent state.

V004 also records a structured `CompensationReport`.

That report distinguishes things such as:

```text
committed receipts
successfully compensated receipts
unrecovered receipts
rollback failures
contract violations
```

This is much better than returning just:

```text
False
```

or:

```text
rollback failed
```

because an enterprise operator needs to know **exactly what remains unresolved**.

# Step 7 — Recovery Service

Now consider a worse case.

A transaction partially commits.

Compensation is attempted.

But one rollback also fails.

The system cannot simply forget about it.

V004 therefore introduces a Recovery Service.

The state becomes conceptually:

```text
normal operation
       ↓
partial failure
       ↓
compensation attempt
       ↓
compensation incomplete
       ↓
recovery required
```

An authorised operator can then attempt recovery.

Two important paths exist:

### Retry rollback

The system tries the failed compensation again.

### Manual resolution

Some situations cannot be repaired automatically.

For example, an external system may have been manually altered.

Then an authorised operator can resolve the recovery record, but evidence is required.

V004 introduced the terminal state:

`MANUALLY_RESOLVED`

That is a good enterprise concept because:

> **manual intervention is not the same as automatic success.**

The audit record should preserve that distinction permanently.

# Step 8 — Append-only lineage/audit

Another important architectural decision is that significant events are recorded rather than overwritten.

Conceptually:

```text

commit C failed

rollback A failed
operator retry attempted
manual resolution evidence attached
record manually resolved
```

An auditor can therefore reconstruct the history.

This is substantially better than simply storing:


because that loses the journey.

For SaaS, especially multi-tenant SaaS, that history matters.
