# 🔴 UF-V008-001 — BLOCKER
## Release handoff verifier can PASS when the declared Final ZIP SHA-256 is wrong

**File**

`scripts/package_release.py`

**Lines**

Approximately **237–279**, specifically:

```python
recorded = re.findall(r"[0-9a-f]{64}", matching[0].read_text("utf-8"))
actual = _sha256(zip_path)

...

elif actual not in recorded:
```

### Defect

The new G12/handoff verifier does **not parse the `Final ZIP SHA-256` field**.

Instead, it extracts **every 64-character hexadecimal string anywhere in the attestation** and passes if the actual ZIP hash occurs anywhere.

Therefore an attestation can contain:

```text
Final ZIP SHA-256 = WRONG HASH
...
post-smoke hash = ACTUAL HASH
```

and `verify_release_handoff()` still reports:

```text
PASS
```

### I reproduced it directly

I created a synthetic handoff where:

- actual ZIP SHA-256 =
  `ba7816bf8f01cfea414140de5dae2223b00361a396177a9cb410ff61f20015ad`
- **Final ZIP SHA-256 field = `0000...0000`**
- another unrelated attestation field contained the actual hash

V008 returned:

```text
problems []
```

Meaning **the verifier accepted a handoff whose authoritative Final ZIP SHA-256 was deliberately wrong.**

### Why this matters

This defeats the exact invariant V008 claims to have added for the V007 blocker.

The attestation itself says that the final artifact is bound by the stated Final ZIP SHA-256. fileciteturn0file0L8-L17

The code instead proves only:

> “Somewhere inside this document exists the ZIP hash.”

Those are materially different guarantees.

### Impact

**Release integrity / evidence authenticity / artifact identity**

A stale, corrupted, accidentally edited, or maliciously inconsistent attestation could be accepted.

This means **UF-V007-B1-001 is NOT safely closed.**

### Required correction

Parse exactly the authoritative field, for example:

```text
| **Final ZIP SHA-256** | `<64-hex>` |
```

Require:

1. exactly one Final ZIP SHA-256 field;
2. valid lowercase/normalized 64-character SHA-256;
3. exact equality with the actual ZIP hash;
4. expected ZIP filename in the attestation also exactly equals the ZIP filename;
5. reject duplicate authoritative fields.

### Required permanent regression tests

Add at least:

```text
wrong Final ZIP hash + actual hash elsewhere => FAIL
duplicate Final ZIP SHA-256 fields => FAIL
malformed Final ZIP SHA-256 => FAIL
wrong ZIP filename + correct hash => FAIL
correct filename + exact Final ZIP hash => PASS
```

This is a **BLOCKER**, because V008 was specifically supposed to close the artifact-handoff integrity defect.

# 🟡 Additional evidence weakness — should be corrected with V009

I am not making this a separate release blocker yet, but it should be hardened.

V008's clean smoke creates a new environment and executes:

```python
pip install setuptools wheel pytest
```

without pinned versions.

Later the attestation's tool versions are gathered using the **builder interpreter**, not the clean smoke venv:

`scripts/package_release.py:470–476`

```python
_run([sys.executable, "-m", tool, "--version"], ...)
```

Meanwhile smoke uses its own:

```text
smoke-venv/bin/python
```

So the attestation does not cryptographically/procedurally prove that the displayed pytest version is necessarily the one that actually ran the exact-artifact smoke.

The V008 attestation currently reports pytest 9.1.1. fileciteturn0file0L64-L71

### Better implementation

Capture from the smoke environment itself:

```python
vpy -m pytest --version
vpy -m pip freeze
vpy --version
```

and write those values into the attestation.

Pin or lock the review/build dependencies as well if reproducible certification is the goal.
