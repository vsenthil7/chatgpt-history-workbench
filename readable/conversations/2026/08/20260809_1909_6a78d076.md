# Release blockers

## P0-1 — Unresolved uncertain commit becomes false `ROLLED_BACK`

V006 initially handles an invalid receipt correctly: it records an `UncertainCommit` and moves to `COMPENSATION_FAILED`.

But `RecoveryService.retry_rollback()` considers only `unrecovered_receipts`. When that collection is empty, it changes the proposal to `ROLLED_BACK` without checking `uncertain_commits`.

**Files:**

- `src/uraiflow/recovery/service.py:62-117`
- `src/uraiflow/proposal/model.py:35-68`
- `02-architecture/adr/ADR-0017-uncertain-external-commit.md:27-41`

### My reproduced result

```text
Before retry:
status=COMPENSATION_FAILED
external effects=1
unrecovered receipts=0
uncertain commits=1

After retry:
status=ROLLED_BACK
external effects=1
retry compensated=0
uncertain commits=1
```

This directly contradicts ADR-0017’s statement that `ROLLED_BACK` means no external effect remains unaccounted for.

### V007 requirement

The aggregate itself must make `ROLLED_BACK` impossible whenever either of these exists:

```text
unrecovered_receipts != ()
uncertain_commits != ()
```

Do not rely only on service-level branching. Introduce a guarded aggregate command such as `mark_rolled_back()`.

## P0-2 — Timeout after external write also becomes false `ROLLED_BACK`

V006 records uncertainty only when `commit()` returns an invalid receipt.

It does **not** record uncertainty when the adapter performs the external operation and then raises an exception—for example, when the remote system committed successfully but the response was lost.

**File:**

- `src/uraiflow/pipeline/orchestrator.py:201-207`
- `src/uraiflow/pipeline/orchestrator.py:208-243`
- `src/uraiflow/pipeline/orchestrator.py:259-295`

### My test adapter

```python
self.effects.append(record.record_id)
raise TimeoutError("response lost after remote commit")
```

### V006 result

```text
status=ROLLED_BACK
external effects=1
uncertain commits=0
recovery uncertain commits=0
failure="raises: TimeoutError: response lost after remote commit"
```

### V007 requirement

The adapter contract must distinguish:

- **Definitely not committed**
- **Committed**
- **Outcome unknown**

A timeout, connection reset, process interruption, or other exception after dispatch must default to **unknown/uncertain**, unless an exact typed exception proves no remote effect occurred.

## P0-3 — Duplicate display names bypass rollback preflight

ADR-0010 explicitly permits duplicate display names and says display names must never affect routing or rollback.

However, preflight stores capabilities in a dictionary keyed by display name:

```python
registered_by_name[registered.descriptor.name] = (
    registered.descriptor.supports_rollback
)
```

**File:**

- `src/uraiflow/pipeline/orchestrator.py:303-322`

I registered:

- Adapter A: `adp.nonrollback`, name `same-display`, rollback **false**
- Adapter B: `adp.second`, name `same-display`, rollback **true**

Adapter B overwrote Adapter A in the preflight dictionary.

### Reproduced result

```text
preflight_blocked=False
status=COMPENSATION_FAILED
nonrollback_external_commits=1
```

The first adapter committed, the second failed, and the first could not be rolled back.

### V007 requirement

Preflight must use `adapter_id`, never display name. Name can appear only as additional human-readable evidence.

## P0-4 — Human-approved content can change before commit

The central UraiFlow promise is:

```text
Proposal → Human confirmation → Commit approved content
```

But `Proposal.items`, `ProposalItem`, and `ProposalItem.fields` remain publicly mutable.

**Files:**

- `src/uraiflow/proposal/model.py:83-112`
- `src/uraiflow/proposal/model.py:115-139`
- `src/uraiflow/pipeline/orchestrator.py:178-200`

### My reproduction

1. Ingested title `approved`.
2. Called the governed `confirm_all()`.
3. Changed the title directly to `NOT_APPROVED`.
4. Called commit.

### Result

```text
confirmed_value="approved"
committed_value="NOT_APPROVED"
status=COMMITTED
failure=None
```

I also confirmed that direct writes to `item.decision` and `proposal.status` can bypass the confirmation service entirely.

### V007 requirement

Confirmation must create a **deeply immutable confirmed snapshot**, including a canonical version or hash.

Commit must use that exact snapshot—not the current mutable proposal object.

Any post-confirmation edit must:

1. Invalidate confirmation.
2. Require revalidation.
3. Require human reconfirmation.
4. Produce a new confirmation version/hash.
