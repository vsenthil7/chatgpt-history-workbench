## F02 — BLOCKER: several public commands use two transactions

The following `WorkObjectRegistry` operations read or validate outside the later write transaction:

- `assign`
- `resume`
- `block`
- `unblock`
- `restart_after_rework`

The most serious reproduced case is `block()`. It reads the object's current state, closes that read transaction, and later enters another transaction to perform the transition.

I inserted a valid `mark_assignable` commit between those two transactions.

### Executed result

```text

P2_STALE_BLOCKED_FROM READY
P2_EXPECTED_BLOCKED_FROM ASSIGNABLE
```

The object was actually `ASSIGNABLE` when it was blocked, but V013 persisted `blocked_from=READY`. A later unblock therefore restores the wrong state.

This is a deterministic **time-of-check/time-of-use state corruption**, not merely a hypothetical race.

### Required V014 fix

Each public mutating operation must put the complete sequence inside one `UnitOfWork.run()` callback:

```text

→ principal/membership validation
→ aggregate load
→ operation preconditions
→ state derivation
→ mutation
→ persistence
→ audit
```
