# 1. 🔴 Major — UraiFlow has already leaked domain semantics into reusable product code

This is the biggest finding.

Claude correctly wrote ADR-0002:

> UraiFlow ships no work-object taxonomy.

`CandidateRecord.record_type` is documented as an **opaque string**.

But then reusable production code contains:

`src/uraiflow/extraction/extractor.py`

with hard-coded understanding of:

- `time_entry`
- `follow_up`
- `availability`
- `contact`
- `minutes`
- `note`
- `window`
- phrases such as `"spoke to"`
- `"follow up"`
- `"available"`

That means UraiFlow itself currently knows what a timesheet entry, follow-up and availability record mean.

That contradicts the architecture Claude just established.

The problem is **not that IPBS appears by name**. The architecture guard successfully prevents that.

The deeper problem is:

> **Tenant-neutral ≠ domain-neutral.**

A reusable UraiFlow SaaS product cannot hard-code the semantic model of the first consuming workforce/timesheet product simply because the string `IPBS` is absent.

### What it should become

UraiFlow should own the **generic extraction mechanism**.

Something outside reusable core should supply:

- extraction schema,
- candidate type definitions,
- field definitions,
- prompt/rules/schema configuration,
- receiving adapter capabilities.

For example, the current rule-based extractor could remain as:

- a test fixture,
- sample/example plugin,
- acceptance fixture,

but **not as reusable UraiFlow domain behaviour**.

This must be fixed in V003 before more functionality grows around it.

# 2. 🔴 State-machine invariant can be corrupted after a failed transition

I reproduced this independently.

Current `ConfirmationService.confirm_all()` does this:

```python
for item in proposal.items:
    item.decision = ItemDecision.CONFIRMED

self._finalize(...)
```

Only `_finalize()` calls `proposal.advance()`.

Therefore, if a proposal is already `REJECTED`, calling `confirm_all()`:

1. changes all its items to `CONFIRMED`;
2. then attempts `REJECTED → CONFIRMED`;
3. raises `InvalidTransitionError`;
4. **but leaves the item decisions mutated.**

I reproduced:

```text
status ProposalStatus.REJECTED
decision ItemDecision.CONFIRMED
```

So the aggregate becomes internally contradictory:

**Proposal state:** REJECTED  
**Item decision:** CONFIRMED

This is a genuine defect despite **100% branch coverage**.

### Required fix

State eligibility must be checked **before any mutation**.

Confirmation operations should be atomic at aggregate level.

Ideally the aggregate itself owns operations such as:

- `confirm_all()`
- `confirm_selected()`
- `reject_all()`
- `edit_item()`

rather than having a service mutate internal state and subsequently ask the aggregate whether the transition was legal.

# 3. 🔴 Terminal proposals remain editable

I also independently confirmed:

```python
proposal.edit_item(...)
```

can modify a proposal after it has become:

- `REJECTED`
- `COMMITTED`
- `ROLLED_BACK`
- etc.

There is currently no state guard inside `edit_item()`.

Therefore historical evidence can effectively be rewritten after business completion.

For a lineage/audit-oriented product, that is not acceptable.

At minimum:

**Editing should only be allowed in explicitly editable states**, probably something like:

`AWAITING_CONFIRMATION`

and later whatever clarification/review state is defined.

After commit/rejection/rollback the proposal should be immutable.

---

# 4. 🔴 “Atomic across adapters” is currently stronger than the implementation guarantees

The RTM says:

> Commit is atomic across adapters.

And Claude reports:

> partial failure compensates committed records and rolls back.

The happy compensation scenario is tested and works.

But production failure handling has important holes.

The orchestrator only catches:

```python
except UraiFlowError
```

A real external adapter/provider can very reasonably throw:

- `TimeoutError`
- `ConnectionError`
- SDK exceptions
- database exceptions
- unexpected runtime errors

If that happens **after one adapter has already committed**, compensation does not execute.

The proposal can remain `COMMITTING`, and a previously committed target record remains committed.

So the implementation currently guarantees:

> atomicity only for failures that adapters correctly translate into `UraiFlowError`.

That is not the same as atomic multi-adapter behaviour.

---

# 5. 🔴 Rollback itself can fail, and that path is not governed

`_compensate()` assumes:

```python
adapter.rollback(...)
```

always succeeds.

If rollback of the first committed target fails:

- exception escapes;
- remaining compensations may never execute;
- proposal is left in `COMMIT_FAILED`;
- `ROLLED_BACK` is never reached;
- there is no dedicated compensation-failure state;
- incomplete rollback evidence is not formalised.

For real SaaS integration, this is exactly the ugly failure path we need to design **now**, while the system is small.

V003 should define something such as:

- `COMPENSATING`
- `COMPENSATION_FAILED`
- `ROLLED_BACK`

or another explicit recovery model.

It also needs tests with:

1. first target commits;
2. second target fails;
3. rollback of first target also fails.

---

# 6. 🟠 `supports_rollback` is declared but atomicity does not enforce it

`AdapterDescriptor` includes:

```python
supports_rollback: bool
```

Good.

But pipeline atomic commit does not ensure all participating adapters actually support rollback before beginning the commit.

Therefore an adapter can legally advertise:

```text
supports_rollback = False
```

while the orchestrator assumes it can compensate it later.

The adapter compliance harness also does not establish that an adapter claiming rollback support can meaningfully honour rollback semantics.

This needs a preflight policy.

---

# 7. 🟠 Adapter contract registration is weaker than claimed

There is an `assert_adapter_contract()` compliance harness, but:

```python
AdapterRegistry.register(adapter)
```

does not invoke it.

That means an invalid adapter can be registered into the actual runtime registry even though tests separately prove that the reference adapter passes the harness.

The contract gate and runtime boundary should not be disconnected like this.

At least validate descriptor invariants during registration.

---

# 8. 🟠 Confirmation selection has an ambiguous behaviour

`confirm_selected()` converts every item not appearing in the provided IDs into:

```text
REJECTED
```

But unknown supplied IDs are silently ignored.

For example:

```text
confirm_selected(["record-that-does-not-exist"])
```

can effectively reject every real item instead of rejecting the command.

That should almost certainly fail fast.

The command should validate:

`selected IDs ⊆ proposal item IDs`

**before making any changes.**

---

# 9. 🟠 Editing does not trigger immediate revalidation

A proposal is:

```text
VALIDATED
→ AWAITING_CONFIRMATION
```

The human can then edit its fields.

Those edits are not validated before confirmation state finalisation.

The target adapter eventually revalidates at commit, which prevents bad storage in the reference adapter, but conceptually the state:

```text
CONFIRMED
```

can refer to content that is no longer valid.

The lifecycle needs to decide deliberately whether an edit:

- returns the item/proposal to validation,
- performs synchronous adapter validation,
- or records an explicit `EDITED_PENDING_VALIDATION` state.
