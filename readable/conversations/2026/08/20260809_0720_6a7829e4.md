# BLOCKER 1 — `candidate_units` is still mathematically wrong

This remains the biggest defect from my first review, but I have now traced it deeper into the contract.

The core model explicitly defines:

```text
candidate_units = units in the source the adapter considered
consumed_units  = units absorbed into an event
unit_name       = message
```

But `parse_export()` does this:

```python
for problem in problems:
    issues.append(...)
    candidate += 1
```

That means **each error increments the supposed number of source messages**.

One source message with 3 validation problems can become:

```text
candidate_units = 3
events = 0
issues = 3
```

even though there was only **one source message**.

Therefore RTM-116:

```text
candidate_units == events + issues
```

does not prove fidelity.

The implementation itself helps manufacture the equality.

### Why this is enterprise-critical

Coverage becomes a measurement of **diagnostic outcomes**, not source coverage.

A source containing 100 messages can theoretically report more than 100 `candidate_units`.

That destroys the semantic meaning of:

```text
412 of 412 messages
```

because the denominator is no longer necessarily messages.

### Required correction

The source-unit lifecycle must be explicit.

A provider-native source unit needs an identity/index such as:

```text
conversation_id
source_unit_index
provider_unit_type
```

Then:

```text
candidate_units = count(distinct source units)
consumed_units = count(source units represented by canonical events)
```

A source unit may have:

```text
0..N ParseIssues
0..N diagnostics
0..N structured blocks
```

without changing its candidate count.

# **BLOCKER F03 — existing “verified” evidence is not revalidated when the evidence database is reopened**

V034 verifies evidence only during `put_evidence()`.

It does not verify already stored evidence when:

- the evidence database is reopened;
- `get_evidence()` is called;
- evidence is iterated;
- a different Event repository is supplied.

That means a durable evidence database can be paired with an Event source against which its evidence no longer verifies.

---

## Exact reproduction

First Event repository:

```text
Event text = "REAL TEXT"
```

I created and stored verified evidence:

```text
excerpt = "REAL"
```

Initial admission:

```text
True
anchor verifies = True
```

I then reopened the same evidence database with another Event source returning:

```text
same Event ID
same SourceRef
same timestamp
changed Event text = "CHANGED!!"
```

V034 reopened normally.

`get_evidence()` returned:

```text
excerpt = "REAL"
```

But:

```text
anchor.verify_against(current_authoritative_event) = False
```

The reported failure is:

```text
the Event text does not match the anchored digest
```

So the durable store returns an object represented as verified evidence even though its currently supplied authoritative Event source disproves it.

---

## Why this is possible

The evidence database is not bound to:

- a particular Event-store identity;
- a particular Event-store schema;
- an Event-store content/version fingerprint;
- an identity scheme;
- a successful full revalidation state.

The Event source is supplied afresh each time the store is opened.

## Required V035 fix

At minimum, opening or reading durable evidence must not silently return an anchor that fails against the supplied authoritative Event repository.

Acceptable designs include:

### Option A — validate on open

```text
open evidence database
    ↓
validate every anchor against supplied Event source
    ↓
refuse if any anchor is missing or invalid
```

### Option B — validate lazily on read

Each retrieved EvidenceItem is checked before being returned.

### Option C — persist and enforce Event-store authority identity

Bind the evidence database to an Event-store identity/snapshot and reject a mismatched store before exposing evidence.

A cache may make this efficient later. Silent mismatch is not acceptable.

# **MEDIUM F06 — the public canonical-identity API has an ambiguous top-level argument**

`canonical_key()` accepts:

```python
fields: Sequence[object]
```

A Python string is a sequence.

Therefore:

```python
canonical_key("d", "ab")
```

is accepted and is exactly equal to:

```python
canonical_key("d", ["a", "b"])
```

Independent result:

```text
string fields vs list fields equal = True
```

This does not affect the current nine `make_id` implementations because they pass lists.

But it contradicts the broad claim that type and arity always participate in the public canonical encoding.

## Required fix

Require the top-level field collection to be an explicit:

```text
list or tuple
```

and reject:

```text
str
bytes
other arbitrary Sequence
```

Also document whether length prefixes are defined in:

```text
UTF-8 bytes
Unicode code points
```

The current code uses Python character counts. A platform-wide canonical scheme should have a language-independent specification before another implementation is written in JavaScript, Java or another language.
