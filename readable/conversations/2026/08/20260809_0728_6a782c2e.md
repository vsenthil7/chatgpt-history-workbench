# New V005 findings

### 🔴 F1 — BLOCKER: Work Object mutation and its mandatory audit event are not atomic

This is the most important remaining architecture problem.

The module-level contract in `workobject/service.py` says:

> every state change ... is audit-recorded and versioned.

But `_transition()` actually does:

1. load object;
2. validate transition;
3. mutate object;
4. `_bump_and_save(updated, event_type)` → **repository state is committed**;
5. `_emit(...)` → only now call `AuditLog.record()`.

Therefore if the audit persistence operation fails after the Work Object repository save, **the command raises an exception but the business mutation survives without its corresponding audit event.**

The same problem exists in more than transitions.

`create()` saves the Work Object **before** emitting `WorkObjectCreated`.

`attach_evidence()` adds the evidence record, modifies/saves the Work Object and **then** emits `EvidenceAdded`.

Consequently an audit failure can produce states such as:

**Work Object exists + no WorkObjectCreated audit event**

or

**state changed/version incremented + no corresponding transition event**

or

**EvidenceRecord persisted + Work Object updated + no EvidenceAdded audit event**.

V009 says the enclosing snapshot protects joined writes.

That statement is only conditionally true:

```text
Nested operation fails
        │

        │          ↓
        │      outer rollback
        │          ↓
        │        SAFE
        │
        └── outer catches exception
                   ↓
              outer commits
                   ↓

                   ↓

```

The architecture currently conflates two different concepts:

```text

```

and

```text
PRESERVE NESTED OPERATION ATOMICITY
```

They are not equivalent.

```text
mutation guard:
```

# BLOCKER — `UnitOfWork.read()` loses its read-only guarantee when it joins a write transaction

V010/ADR-023 introduced a very clear contract:

> `UnitOfWork.read(operation)` executes a consistent read and **mutation inside is rejected**.

The RTM currently marks RD-001 **ENFORCED** and says:

> “read transactions grant no mutation rights.”

At top level, V012 does enforce this correctly. A top-level `read()` starts the serialization domain with `writable=False`, and a store mutation fails.


## Why ADR-025 did not close this

ADR-025 added a **store-scope stack**, which was the correct fix for V011:

```text
outer scope  = {Org, Principal}
inner scope  = {Org}
```

But transaction **mode** is still global:

```python
self._writable = True / False
```

There is no corresponding nested mode stack.

So the coordinator now understands:

```text
"Which stores may the current nested scope mutate?"
```

but not:

```text
"Is the current nested scope itself READ-ONLY or WRITE?"
```

A joined `read()` therefore inherits WRITE authority from its parent.

Conceptually the current frame needs two dimensions:

```text
CURRENT TRANSACTION FRAME

┌───────────────────────────┐
│ stores: {Organisation}    │
│ mode:   READ              │
└───────────────────────────┘
```

rather than treating writability as one property of the outermost lock.
