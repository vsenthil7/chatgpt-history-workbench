# Findings

## 🔴 F01 — Allocation invariants allow impossible states

This is the most important code defect.

`src/cgwo_core/allocation.py:68-76`

The constructor checks:

- tenant matches window
- `plan_item_ref`
- allocated > 0
- consumed >= 0

But it does **not** enforce consistency between:

`allocated_minutes`  
`consumed_minutes`  
`state`

So all of these invalid domain objects are currently constructible:

```text
allocated = 120
consumed = 500
state = RESERVED
```

```text
allocated = 120
consumed = 0
state = CONSUMED
```

```text
allocated = 120
consumed = 50
state = OVERRUN
```

```text
allocated = 120
consumed = 25
state = PROPOSED
```

That means the state machine can be bypassed simply by constructing the dataclass directly.

The tests never attack this.

### Required V003 fix

Define state-dependent invariants such as:

- PROPOSED / RESERVED: consumed = 0
- PARTIALLY_CONSUMED: `0 < consumed < allocated`
- CONSUMED: `consumed == allocated`
- OVERRUN: `consumed > allocated`

And decide valid semantics for CONSUMING / RELEASED.

Add negative construction tests.

This should become a regression/invariant requirement in RTM.

## 🔴 F02 — An allocation can exceed its Capacity Window

`src/cgwo_core/allocation.py:58-76`

Nothing prevents:

```text
CapacityWindow.available_minutes = 60
CapacityAllocation.allocated_minutes = 600
```

That directly contradicts the meaning of a capacity-governed orchestration system.

Even worse, there is currently no aggregate reservation logic preventing:

```text
window capacity = 600 minutes

allocation A = 500
allocation B = 500
allocation C = 500
```

All three can individually exist.

So Claude’s release language around **“capacity conflict detection”** must be carefully limited.

Current implementation provides:

- window overlap detection
- single-allocation consumption overrun detection

It does **not** yet provide:

- reservation capacity protection
- aggregate allocated-capacity conflict
- cross-allocation contention
- cross-window capacity resolution

Claude does acknowledge “cross-window conflict detection” as deferred, but the canonical product scope and some release language make the executable slice sound stronger than it is.

### V003

Either introduce a `CapacityLedger` / reservation policy / allocation aggregate now, or explicitly keep it deferred and prevent a single allocation from exceeding the window at minimum.

`src/cgwo_core/plan_item.py:93-113`
