# 🔴 Finding 1 — Cross-tenant principals can be assigned to another tenant's work

This is the most important defect.

`WorkObjectRegistry.create()` accepts an `owner_id`, and `assign()` accepts an `assignee_id`, but the registry has **no PrincipalRepository/identity validation dependency**.

So the code never checks:

> Does this owner or assignee actually belong to `context.organisation_id`?

I constructed two organisations and principals and tested it.

The delivered V002 code accepted:

```text
foreign owner accepted: prn-000004 org=org-000001
foreign assignee accepted: prn-000004
```

In other words:

**Organisation A can create a Work Object whose owner is a principal belonging to Organisation B.**

Then Organisation A can assign that work to the Organisation B principal.

That contradicts the spirit of the claimed organisation-isolation guarantee.

The current isolation suite tests whether Tenant B can access Tenant A's Work Object, but **does not test foreign-principal injection into a valid Tenant A operation**.

This needs regression tests such as:

- foreign owner rejected;
- foreign assignee rejected;
- foreign requester/acting principal rejected;
- valid same-org principals accepted.

---

# 🔴 Finding 2 — `TenantContext` permits organisation/principal mismatch

This is closely related but even more foundational.

`TenantContext` contains:

```python
organisation_id
principal_id
```

but validates only that both strings are syntactically valid.

It does **not establish that the principal belongs to that organisation**.

I tested:

```text
TenantContext(
    organisation_id = Organisation-A,
    principal_id = Principal-from-Organisation-B
)
```

and V002 successfully created a Work Object.

Result:

```text
mismatched context principal accepted: prn-000004 for org org-000001
```

That means audit events can effectively say:

> Organisation A operation performed by a Principal that actually belongs to Organisation B.

This is not merely the deferred `SEC-001` role/permission problem.

Authorization can remain deferred, but **tenant/principal binding cannot be deferred if DW-FR-013 is marked ENFORCED**.

Claude needs to distinguish:

- authentication;
- tenant identity binding;
- authorization/permissions.

Role permission checking can remain later.

Tenant identity binding cannot.

---

# 🔴 Finding 3 — "immutable audit" is not actually immutable

`EventEnvelope` is declared:

```python
@dataclass(frozen=True, slots=True)
```

which looks immutable.

But it contains:

```python
payload: dict[str, str]
```

A frozen dataclass prevents replacing the `payload` attribute; it does **not make the dictionary immutable**.

I tested the actual delivered implementation:

```python
audit.entries_for(ctx)[0].payload["k"] = "tampered"
```

and then read the audit again.

Result:

```text
{'k': 'tampered'}
```

So an event already stored in the supposedly append-only audit trail can have its payload modified afterwards.

That contradicts descriptions such as:

> append-only audit

and the events module's statement that:

> Events ... are immutable.

This should be fixed structurally, not documented away.

For example, use a truly immutable payload representation or make defensive immutable copies at the envelope/audit boundary.

Add an explicit regression test attempting to mutate a previously recorded audit event.
