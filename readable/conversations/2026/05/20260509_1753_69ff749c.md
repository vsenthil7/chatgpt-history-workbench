## What I understand Verixa to be (in my own words)

**One sentence:** Verixa is a runtime governance layer that sits between an enterprise's AI agents and the world they act on, so that every action those agents take is policy-checked, independently reviewed by three different LLMs, fully replayable, and packaged into a dossier a regulator can audit.

**The shape of the product:**

Imagine a regulated bank deploys an AI agent that can read customer data, call APIs, and execute trades. Today, when the regulator asks "show me what this agent did on May 3rd at 14:22 and prove it followed your policy," the bank cannot answer. Logs are partial. The model itself can't be re-run identically. There's no independent check on the agent's reasoning. There's no Annex IV-ready evidence file.

Verixa is what you install so you can answer that regulator. Specifically:

1. **It intercepts every tool call the agent tries to make.** The agent doesn't get to call `transfer_funds()` directly — Verixa stands in the way.
2. **It runs each intercepted call against a Rego policy.** Rules-as-code: "this agent role cannot transfer over £10k without a human approval token." Policy fails → call denied → logged.
3. **For high-risk decisions, it triggers Triad Review.** Three independent 70B models — Qwen3, Llama-3.3, DeepSeek-V3 — each get the same package, each commit a hash of their verdict before any of them sees the others' answers (so they can't herd). Then they reveal. Disagreement = escalation. Agreement = strong evidence.
4. **It logs the full picture to an append-only signed ledger.** Hash chain, Ed25519 signatures, tamper-evident.
5. **It pins enough state to replay the decision bit-for-bit later.** Model weights hash, prompt, tool definitions, RNG seed — pinned to the ledger entry. Regulator asks "show me May 3rd 14:22" → Verixa replays it identically.
6. **On request, it generates the Annex IV / Article 9-15 / Article 72 dossier.** PDF + JSON + signed hash chain. The thing the regulator actually wants in their hand.

**Why it's defensible:**
- The existing AI-GRC vendors (Credo, Holistic, Trustible) are SaaS — your governance layer sits in *their* cloud, calling *their* LLMs. A bank or defence ministry cannot send sensitive prompts to someone else's cloud to be governed. Verixa runs sovereign on the customer's own AMD MI300X.
- AAGATE (the Cloud Security Alliance reference architecture, Nov 2025) is a paper. The GitHub repo is a Next.js dashboard with mock data. Verixa is the working implementation of what the paper describes — plus four things the paper itself doesn't have: sovereign on-prem inference, multi-model triad (paper has a single "Janus mirror"), deterministic replay, and the Annex IV dossier.
- One MI300X has 192GB HBM3 — enough memory to run all three 70B models at full precision on a single card. That's the AMD-specific reason this architecture is buildable now.

**Buyer:** CIO / CISO / Head of AI Governance at a regulated UK or EU mid-to-large enterprise. Specifically: financial services, healthcare, public sector, defence, energy. The buyer's pain is "I cannot deploy AI agents in production because I cannot prove to my regulator that they're governed."

**Pricing shape:** £150k pilot, £500k+ full deployment. Land-and-expand into broader governance over time.

**What it isn't:**
- Not a model-evaluation harness (that's the future "Bench" module)
- Not a model-attestation/provenance product (future "Hallmark")
- Not a digital-twin replay sandbox as a standalone product (replay is a feature, not the product)
- Not a Rego policy authoring IDE (future "Forge")
- Not a chatbot, not an agent itself, not an LLM router

For the hackathon and for the £150k pilot conversation, **only the runtime governance product ships**. Bench / Hallmark / Replica / Forge are clearly labelled as future modules in the roadmap section, not promised today.

## Things I am genuinely unsure about — please clarify

These are the questions where I would otherwise either guess or hedge in the docs. I'd rather you sort them now.

### Block A — Product scope and boundary

**A1.** When Verixa "intercepts a tool call," what is the **integration mechanism** the customer adopts? Three plausible patterns, each with very different architecture implications:
- (i) Verixa exposes an OpenAI-compatible proxy endpoint, customer points their agent's LLM client at Verixa instead of OpenAI/Anthropic
- (ii) Verixa provides an SDK the customer wraps their tool functions in (`@verixa.govern` decorator pattern)
- (iii) Verixa is a sidecar in the customer's Kubernetes cluster, intercepts via service mesh (Istio/Cilium, AAGATE-style)
- All three?

**A2.** Is Verixa **only governing AI agents the customer builds**, or also **third-party AI products the customer buys** (Microsoft Copilot, Salesforce Einstein, etc.)? The second is much harder — you can't always intercept tool calls inside someone else's SaaS.

**A3.** "Runtime governance" — does this include **input-side filtering** (prompt injection detection, PII redaction before the LLM sees it), or only **output-side / action-side** (tool calls, generated content)? AAGATE covers both. What does Verixa cover at MVP?

**A4.** Does Verixa itself **run the customer's LLM inference** (i.e. customer's agents make calls through Verixa, which then calls the underlying model on the same MI300X), or does Verixa only **observe and gate** while inference runs elsewhere on the customer's infrastructure?

### Block B — Triad Review specifics

**B1.** **What triggers Triad Review?** Every tool call (expensive — three 70B inferences per agent action)? Or only when policy flags "high-risk"? Or sampled (e.g. 5% of calls + 100% of high-risk)?

**B2.** When the three models disagree, what happens? Block the action and escalate to a human? Default to majority vote? Default to most-conservative verdict? Different per policy?
