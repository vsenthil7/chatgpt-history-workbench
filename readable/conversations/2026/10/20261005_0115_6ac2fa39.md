## Part 1 — What is a credential?

Forget TalkProof for one minute.

Suppose you have an account with an external service and it gives your software something like:

```text
[REDACTED:openai-anthropic-key:sha256-c23d2ceeb55d]
```

That value tells the external service:

> "The software presenting this secret is authorised to use this account."

For software-to-software communication, this is often called an:

**API key / credential / secret / token**

They aren't always technically identical, but **for today's mental model**, think:

> **Credential = machine password allowing TalkProof to use another system.**

### Why does TalkProof need them?

TalkProof doesn't physically own every external capability.

For example:

```text
TalkProof
    │
    ├── needs AI
    │      ↓
    │   AI provider
    │
    ├── needs telephone call
    │      ↓
    │   telecom provider
    │
    └── needs another external service
           ↓
        provider
```

Those providers need to know **whose authorised account TalkProof is using**.

That's where credentials enter.

# Part 2 — BYO versus platform credentials

This distinction is very important in TalkProof.

Imagine two customers:

```text
Tenant A
Tenant B
```

Tenant A might say:

> "I already have my own provider account. Use **my API key**."

That's **BYO — Bring Your Own credential**.

So:

```text
Tenant A
   │
   └── A's provider API key
```

But another tenant might not have one.

TalkProof may have a **platform-owned provider account**:

```text
TalkProof platform
   │
   └── Platform provider API key
```

Therefore TalkProof's intended decision can become:

```text
Tenant requests provider
        │
        ▼
Does this tenant have usable BYO?
        │
   YES ─┴─ NO
    │       │
    ▼       ▼
Use BYO   Is platform key available?
             │
        YES ─┴─ NO
         │       │
         ▼       ▼
     Platform    503
               unavailable
```

### LEARN NOW

Keep this simple rule:

> **BYO belongs to the tenant. Platform credential belongs to the platform.**

# Part 3 — Plaintext

Suppose the actual key is:

```text
[REDACTED:openai-anthropic-key:sha256-5d12d217919f]
```

When we can see and use the actual secret, that is essentially its **plaintext** form.

And there is an unavoidable engineering reality:

> At some point TalkProof must have the usable secret because it must give authentication information to the external provider.

So the security requirement cannot simply be:

> "Never decrypt the key."

If it were never usable, TalkProof couldn't authenticate.

Instead:

> **Keep it encrypted while stored. Decrypt only when necessary. Minimise where plaintext travels.**

# Part 5 — But eventually it must be decrypted

Now TalkProof wants to make an actual provider call.

Conceptually:

```text
DATABASE
encrypted credential
       │
       ▼
Credential Resolver
       │
       ▼
    DECRYPT
       │
       ▼
plaintext credential
       │
       ▼
Provider adapter
       │
       ▼
Internet
       │
       ▼
External provider
```

That decrypted secret should have a **very small life**.

We don't want:

```text
decrypt
   ↓
write plaintext to DB
   ↓
put plaintext in logs
   ↓
put plaintext in audit
   ↓
return plaintext to browser
```

We want:

```text
decrypt
   ↓
use for provider operation
   ↓
don't persist/log/return it
```

The current `ResolvedCredential` explicitly represents this runtime credential, and its `repr` masks the secret rather than displaying the plaintext. fileciteturn6file0

# Part 6 — Masking is NOT encryption

This is an important distinction.

Suppose:

```text
Real key:
sk-abcdefghijklmnop
```

TalkProof might display something like:

```text
sk-ab***mnop
```

That's **masking**.

It helps a human recognise:

> "Yes, that's probably the key I entered."

But the masked value cannot authenticate with the provider.

Think of your bank card:

```text
Real:
1234 5678 9012 3456

Displayed:
**** **** **** 3456
```

That isn't encryption.

It's simply hiding most of the value **for display**.

### Mental model

| Form | Purpose |
|---|---|
| Plaintext | Actually usable secret |
| Encrypted | Safe-ish persistent representation |
| Masked | Human-readable preview |

That's one of the most important distinctions in today's lesson.

> **Choosing the right credential means choosing both the right provider AND the right tenant.**

# Part 8 — What is the Resolver?

The **ProviderRouter / credential resolver** is basically the decision-maker.

Its job isn't to perform AI inference itself.

Its job is closer to:

```text
"Senthil's tenant wants OpenAI."

        ↓

Do we have Senthil tenant BYO?

        ↓

Is it usable?

        ↓

Is its spend cap okay?

        ↓

YES → decrypt that credential

otherwise

        ↓

Is platform credential available?

        ↓

YES → decrypt platform credential

otherwise

        ↓

503 provider_unavailable
```

The current `ProviderRouter.resolve_credential()` implements this selection/decryption path. fileciteturn6file0
