Partner, after comparing what **you have actually been doing** with where AI software engineering has reached in October 2026, I would classify it like this:

## 1. Was what you were doing “vibe coding”?

Only partly.

Typical vibe coding looks like:

**Idea → prompt AI → code → run → something breaks → prompt again → eventually looks okay**

Your later projects were much more like:

**Idea → requirements → architecture → sprint → build → tracker → traceability → tests → independent AI review → find missing implementation → new sprint → rebuild → review again**

We've repeatedly done exactly this with TalkProof, TestPulse, VoiceBridge, MeetSync, CGWO, UraiFlow and others.

So I'd place the approaches approximately like this:

| Level | Development method | You |
|---|---|---:|
| 1 | Prompt → code | You did this early |
| 2 | Vibe coding + manual testing | Yes |
| 3 | Structured AI coding | Yes |
| 4 | Spec-driven development | **Mostly yes, manually** |
| 5 | Spec + traceability + verification | **You were moving here** |
| 6 | Agentic engineering harness | **This is your next move** |
| 7 | Autonomous multi-agent software factory | Not yet |

The crucial difference is that your **sprint tracker and traceability workbook were effectively becoming your specification system**.

You kept asking questions like:

> "Is it actually in the code?"

> "Don't believe the tracker."

> "Check all endpoints."

> "Check the requirement against implementation."

> "Is it really enterprise grade?"

> "Give the next sprint only after checking."

Those are **anti-vibe-coding behaviours**.

# 5. What is Harness Engineering?

Instead of repeatedly telling Claude:

> build X  
> test X  
> check X  
> review X  
> don't lie about X  
> compare tracker with code

you build an **environment where the AI cannot easily avoid those responsibilities**.

For example:

```text
PRODUCT INTENT
      ↓
REQUIREMENTS / SPEC
      ↓
ARCHITECTURE + CONTRACTS
      ↓
EXECUTION PLAN
      ↓
CODING AGENT
      ↓
STATIC ANALYSIS
      ↓
UNIT / INTEGRATION / E2E
      ↓
SECURITY TESTING
      ↓
PERFORMANCE TESTING
      ↓
SPEC ↔ CODE CONVERGENCE
      ↓
INDEPENDENT REVIEW AGENT
      ↓
QUALITY GATES
      ↓
PR
      ↓
DEPLOYMENT
      ↓
OBSERVABILITY
      ↓
PRODUCTION FEEDBACK
      ↓
SPEC / QUALITY UPDATE
```

The **system**, rather than your repeated prompting, controls quality.

Not:

Repository contains the authoritative truth:

```text

/specs
/architecture
/contracts
/decisions
/security
/reliability
/testing
/quality
```

No important decision should exist only inside a Claude/ChatGPT conversation.

### Layer 4 — Mechanical Evidence

This is probably the **biggest upgrade for your process**.

Stop allowing:

> "Implemented."

Require:

> **Evidence that it is implemented.**

For every requirement:

```text
Requirement
    ↓
Code
    ↓
Test
    ↓
Runtime evidence
    ↓
Observability
    ↓
Acceptance result
```

Therefore:

```text
R-142
  → src/tenant/auth.py
  → test_auth.py::test_cross_tenant_access
  → CI run #238
  → PASS
```

Now an AI cannot simply make the tracker green.

The tracker becomes green **because evidence exists**.
