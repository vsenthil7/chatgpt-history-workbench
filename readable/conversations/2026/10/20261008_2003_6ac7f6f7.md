### Brain squeeze

Partner, **your challenge is correct**.

If the system already receives this:

```text
order_id = 456
refund_amount = 120
```

then **we may not need an LLM at all.**

Normal code can do:

```text
authenticate
→ authorize
→ verify tenant
→ find order 456
→ verify refund eligibility
→ verify not already refunded
→ check £120 <= £500
→ refund
```

The LLM becomes useful because the **input is human language**, such as:

> "I'm bloody furious. That thing I bought yesterday was a mistake. Just give me my money back."

Now ordinary deterministic code has a harder problem: **what exactly does this person mean?**

---

## Deep explanation — you found the missing architecture

You said:

> *"LLM may standardize it and give it to deterministic code as a standard one."*

**Exactly. That's the important idea.**

Think of the LLM as an **unstructured → structured translator**, not the authority.

Human says:

```text
"I'm furious. Refund the £120 I paid for order 456."
```

LLM might produce:

```json
{
  "intent": "refund_request",
  "order_id": "456",
  "requested_amount": 120,
  "sentiment": "angry"
}
```

Then we **do not trust that JSON merely because the LLM produced it.**

The deterministic system validates it:

```text
Is intent allowed?
Is order_id valid?
Does order 456 actually exist?
Does authenticated user own it?
Correct tenant?
Actual refundable amount really £120?
Already refunded?
Refund still permitted?
£120 <= £500?
```

Only then:

```text
execute_refund()
```

### But you spotted another problem

You said the LLM itself is probabilistic, so:

> how can variable LLM output feed deterministic code?

Excellent question.

We constrain the **interface**.

Instead of asking:

> "What should we do with this customer?"

we ask the model to produce a defined structure such as:

```text
intent: one of [
    refund_request,
    order_status,
    complaint,
    unknown
]

order_id: string | null
amount: number | null
sentiment: angry | neutral | positive
```

Then normal code validates that structure.

If the LLM returns garbage, missing information or low-confidence/ambiguous information:

```text
DON'T REFUND
```

The system can ask:

> "Which order would you like refunded?"

So the deterministic boundary begins **immediately after the probabilistic interpretation**.

---

## Your database/MCP question is even more important

You asked whether the LLM should itself access the database.

Usually, I would **not give the LLM unrestricted database access**.

Better architecture:

```text
LLM
 ↓
approved tool/API
 ↓
deterministic validation + authorization
 ↓
database
```

For example, the model can request:

```text
get_order(order_id=456)
```

But the tool implementation determines:

```python
get_order(
    authenticated_user=current_user,
    tenant=current_tenant,
    order_id=456
)
```

The model doesn't get to say:

```sql
SELECT * FROM everything;
```

And your MCP point is important:

**MCP can provide the connection/tool mechanism. It does not automatically provide the security.**

You still need authorization, tenant isolation, validation and controlled tool permissions behind that interface.

---

## So when should we NOT use an LLM?

This is important for an AI engineer.

If your application already receives:

```json
{
  "order_id": 456,
  "refund_amount": 120
}
```

from a normal form, **don't insert an LLM merely because this is an AI application.**

That's extra:

- cost,
- latency,
- nondeterminism,
- failure modes,
- attack surface.

Your instinct — *"why am I paying an LLM to do something Python can reliably do?"* — is exactly the engineering question you should ask.

### Your resilience answer

Your central idea is good — and there is an industry pattern very close to what you just designed yourself.

You said, in effect:

```text
LLM starts failing
       ↓
do not let 1,000 requests independently hammer it
       ↓
central state says dependency unhealthy
       ↓
hold/reject/queue work
       ↓
allow a small health test
       ↓
when healthy, allow traffic again
```

That is very close to a **circuit breaker**.

A common mental model is:

```text
CLOSED
normal traffic allowed
   ↓ failures cross threshold

OPEN
stop calling unhealthy LLM
fail fast / degrade / queue where appropriate
   ↓ after cooldown

HALF-OPEN
allow only a few test requests
   ↓ success                 ↓ failure
CLOSED                       OPEN
```

So your important insight is correct: **1,000 failed requests should not automatically create another 1,000 immediate retries.** That can make an already struggling provider worse and also waste tokens/cost.

There are two corrections to your design.

First, I would **not make every waiting request loop and repeatedly query a database table**. If 100,000 requests do that, we have simply moved the hammering problem from the LLM to our database. The circuit-breaker state is normally checked very cheaply by the application/service layer; requests can fail fast, degrade, or be queued depending on the product.

Second, a heartbeat alone is not enough. A health endpoint may answer `OK` while real LLM requests are taking 15 seconds. The breaker should also learn from **actual request failures, timeout rate and latency**.

For retries themselves, we add another mechanism:

> **bounded retry + exponential backoff + jitter**

Not:

```text
fail → retry immediately → retry immediately → retry immediately
```

but conceptually:

```text
fail
 ↓
wait a little + random variation
 ↓
retry
 ↓
wait longer + random variation
 ↓
retry
 ↓
STOP after configured limit
```

The random variation (**jitter**) matters because otherwise thousands of clients can all wake up at exactly the same moment and attack the provider again.

**Queue** = should this work wait and be processed asynchronously later?

### One correction: FIFO is not always enough

FIFO is a reasonable default, but production systems may need priorities. An interactive user waiting on-screen may have a different deadline from a background summarisation job.

Also, old queued chat requests can become **stale**. After 20 minutes, the user may have left or sent a newer message. So before replaying the backlog, we may check **deadline / cancellation / staleness**, rather than blindly executing everything.

### What you have just described
