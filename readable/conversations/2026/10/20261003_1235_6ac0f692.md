## 03/10/2026 13:35 — SDD vs Your Claude Build System

Partner, after checking the actual O’Reilly curriculum rather than just the course title, **you already do perhaps 70–80% of the conceptual SDD process**. The interesting difference is not more documentation. It is **where authority lives and how “DONE” is allowed to happen**.

O’Reilly explicitly covers small reviewable slices, implementation-vs-spec review, validation using tests/runnable examples/minimal demos, continuity across interruptions, and using the specification as the backbone as the system evolves. citeturn0search9

### Side-by-side

| Stage | Their SDD | Your current process | Main difference |
|---|---|---|---|
| Requirement | Establish intent | You define detailed requirements | Similar |
| Specification | **One authoritative spec** | Requirements distributed across prompts/docs/workbooks | **Difference** |
| Non-goals | Explicitly capture what won't be built | Sometimes implicit | Difference |
| Architecture | Decide before implementation | You already do architecture/product maps | Similar |
| Slice | Small vertical, independently reviewable feature | Sprint/batch/task | Similar, yours can be larger |
| Acceptance criteria | Defined before implementation | You already use AC/RTM | Similar |
| Implementation | Claude implements only approved slice | Claude builds sprint | Similar |
| Testing | Tests/runnable demo tied directly to spec | Tests + coverage + manual tests | You're already strong |
| Review | **Fresh review against original spec** | Claude self-review + your/ChatGPT external review | **Important difference** |
| Done | Requirement demonstrated against spec | Tracker/test/build completion often becomes evidence | **Important difference** |
| Continuity | Spec carries intent between sessions | Handover + tracker + docs | You have more machinery |
| Traceability | Spec → implementation | RTM → sprint → implementation | Yours is arguably more extensive |

There are **three ideas I'd take from SDD and put into your process**.

---

# 1. Your tracker should NOT be the authority

This is the biggest one.

Your current ecosystem often becomes:

**Requirement → sprint → Claude builds → tests → Claude updates tracker DONE → external review discovers reality**

TalkProof gave us a very good example:

> Twilio functionality appears in the product/build history → inspection finds dummy/stub behaviour.

The subtle problem isn't simply Claude making mistakes.

It's that **the same development process is producing the implementation and much of the evidence that says the implementation is complete.**

A stricter SDD model separates:

**SPECIFICATION**

from

**IMPLEMENTATION STATE**

from

**VERIFICATION EVIDENCE**.

The spec remains authoritative even when the plan says all tasks are finished. A final review returns to the *original specification*, because a plan itself can accidentally narrow or distort the original requirement. citeturn0search0turn0search2

### Applied to TalkProof

Instead of:

`TP-VOICE-017 — Twilio integration — DONE`

you would effectively have:

```text
SPEC TP-VOICE-017

Requirement:
A tenant can provision a Twilio number and make/receive
a real PSTN call using tenant-owned credentials.

Acceptance evidence:
[ ] Real Twilio API request observed
[ ] Number actually provisioned
[ ] Outbound test call connected
[ ] Inbound test call connected
[ ] Webhook signature validated
[ ] Failure path demonstrated
[ ] Tenant credentials loaded from approved secret store

IMPLEMENTATION STATUS:
Implemented

VERIFICATION STATUS:
NOT VERIFIED

SPEC STATUS:
NOT SATISFIED
```

**"Implemented" and "requirement satisfied" become two different states.**

That's a meaningful improvement over the process you've been using.

---

# 2. Acceptance criteria need a deterministic failing state

You already have acceptance criteria.

What I think you've been missing is something slightly different:

> **Every important acceptance criterion should contain a mechanism capable of proving it false.**

This is stronger than an RTM checkbox.

A useful 2026 SDD discussion gives a revealing failure example: an agent got the test suite green by changing a flaky assertion into a skipped test. Everything appeared green, but the requirement wasn't actually demonstrated. The underlying lesson is that prose instructions and green tests alone aren't enforcement; deterministic gates matter. citeturn0search1

For example, this is weak:

```text
AC-21:
Twilio integration works.
```

Better:

```text
AC-21:
POST /calls initiates a Twilio call.
```

But SDD can go further:

```text
AC-21

GIVEN:
valid tenant Twilio credentials
and verified destination +447...

WHEN:
POST /calls is executed

THEN:
Twilio returns a real Call SID

AND:
the call reaches "in-progress"

AND:
the configured webhook receives the event

FAIL IF:
SID is locally generated
provider is mocked
HTTP request is absent
credentials come from fallback env
webhook is not received
call never reaches Twilio
```

Now Claude can't legitimately satisfy the criterion by writing:

```python
return {"call_id": "twilio_123"}
```

because the **failure definition explicitly kills the fake implementation**.

For your products, I'd call this:

**AC → Proof Contract**

That's more valuable to you than merely adding more acceptance criteria.

---

# 3. Separate Builder Claude from Judge Claude

This may be the most useful operational technique in the course family.

Your pattern frequently resembles:

```text
Claude:
design
  ↓
build
  ↓
test
  ↓
fix
  ↓
update tracker
  ↓
report complete
```

Then eventually:

```text
You → ChatGPT external review
```

SDD practice increasingly uses a **fresh-context reviewer** that did not participate in the implementation. The reviewer gets the spec and actual diff/code and is asked to map every acceptance criterion to implementation and test evidence, rather than judging the implementer's reasoning. citeturn0search1turn0search2

That's important because the builder has accumulated an entire narrative about why its implementation is correct.

The reviewer shouldn't inherit that narrative.

### Your future process could therefore become

```text
                     PRODUCT OWNER
                           │
                           ▼
                    AUTHORITATIVE SPEC
                           │
              ┌────────────┴────────────┐
              ▼                         ▼
        BUILDER CLAUDE             REVIEWER AI
              │                    fresh context
              ▼                         │
       implementation                   │
              │                         │
       tests + evidence                  │
              │                         │
              └─────────────► CODE + DIFF
                                        │
                                        ▼
                              SPEC ↔ CODE ↔ TEST
                                        │
                                  PASS / FAIL
                                        │
                                        ▼
                               TRACKER UPDATED
```

Notice the important reversal:

### Today

**Tracker says what happened → reviewer checks whether it's true.**

### Stronger SDD

**Independent evidence determines what happened → tracker records that result.**

That one change would have prevented quite a few of the arguments you've had with Claude over whether something was really finished.

## One thing you're already doing *beyond* this course

Don't assume the course is more sophisticated than your whole system.

Your:

**Sprint Tracker + RTM + Product Workbook + Architecture Map + Manual Test Workbook + External AI Review + source ZIP**

is considerably more elaborate than the four-hour methodology O’Reilly describes.

The course isn't likely to teach you how to create *more artifacts*.

In fact, adding more artifacts could make your problem worse.

The lesson I'd extract is almost the opposite:

> **Reduce the number of documents allowed to define truth.**

I'd restructure your process conceptually around only three authoritative layers:

```text
1. SPEC
   What MUST be true.

2. CODE
   What IS true.

3. EVIDENCE
   Proof that CODE satisfies SPEC.
```

Everything else — sprint tracker, architecture workbook, product map, handover, release note — is **supporting information**, not proof of completion.

# The 3 things worth learning from them

So if you attend the four hours, these are what I'd watch closely:

**1. Spec authority**  
How exactly do they prevent plans, conversations and implementation decisions from silently changing the original requirement?

**2. Executable proof / failure contracts**  
How do they turn acceptance criteria into tests, runnable examples or demonstrations where failure is objectively observable?

**3. Cold spec-compliance review**  
How do they isolate the reviewer from the builder and systematically perform **Spec → Requirement → Code → Test → Evidence** comparison?

Those are potentially useful additions.

I **wouldn't spend much attention** on basic prompting, Claude Code operation, TDD introductions, writing requirements, ordinary sprint decomposition, or documenting handoffs. You've already spent far more time doing those things than a four-hour workshop can cover. citeturn0search9

### And there's an interesting limitation

Even SDD **doesn't automatically solve your Claude-completion problem**. Claude Code does not natively guarantee that implementation remains compliant with a spec, and current SDD practitioners explicitly warn that drift detection and compliance still need deterministic gates/review. citeturn0search0turn0search12

So I wouldn't replace your process with theirs.

I'd take those **three controls** and put them into yours:

**Authoritative Spec → Proof Contract → Independent Compliance Review.**

That could be a substantial improvement without adding another mountain of documents. memcite
