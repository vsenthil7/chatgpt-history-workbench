## 2. Exam overview, Part 2 (8:29)

The one idea behind all five domains: decide which parts of the system may be probabilistic and which must be guaranteed.

**Key points**

- The model follows prompt rules most of the time, not every time. A hard business limit (for example a refund cap) belongs in code at the tool-call boundary.
- Each domain is framed as an engineering decision, not a topic to memorise.
- Choose the simplest architecture that works: fixed workflow first, adaptive agent when steps vary, multi-agent only when needed.
- Tool choice gets less accurate once one agent has more than about five tools.
- Tool design is information design: clear descriptions and useful, structured error messages.
- Four reliability layers: structure (format), meaning (values), behaviour (actions), session (state over time).

**Exam traps**

- Valid JSON does not mean the values inside are correct.
- Enforcing rules only through the prompt.
- Ending a loop because the model's text says it is done, instead of checking stop_reason.
- Escalating to a human based on detected sentiment instead of clear rules.

## 3. Claude doesn't run your tools (6:51)

Claude only requests a tool call; your code runs the tool and sends the result back.

**Key points**

- Every Claude system is built from three parts: model calls, tool calls, and context.
- A request has three main pieces: the system prompt, the list of tools, and the messages array.
- The response's stop_reason tells your loop what to do next.
- Handshake: Claude returns a tool_use block with an ID; you run the tool; you send back a tool_result carrying the same ID.
- Tool results go back in a **user** message, not an assistant message.
- The video walks through a full four-turn exchange from first question to final answer.

**Exam traps**

- Thinking the model executes code or calls APIs itself.
- A tool_result ID that doesn't match its tool_use ID.
- Putting the tool result in the assistant role.

## 4. Inside Claude Code: live demo (5:56)

A practical follow-up to video 3: every request Claude Code sends is logged and walked through.

**Key points**

- One prompt from you can trigger several API calls behind the scenes.
- Context grows with each turn: earlier messages, tool calls and tool results are all re-sent.
- When Claude Code needs a tool (read a file, run a command), the model asks, Claude Code runs it locally, and the result goes back in the next call.
- The final answer you see is assembled only after the model stops asking for tools.

**Why it matters for the exam:** it makes the agent loop and context growth concrete, which helps with the context-management and Claude Code questions.

## 5. Sessions, resume and fork (6:54)

A resumed session works from what it read earlier, so if the files changed since, it can act on stale content with full confidence. Mapped to Domain 1, Task 1.7.

**Key points**

- The agent has no memory of its own; a session is a saved conversation log stored on your disk.
- When the agent reads a file, it keeps a snapshot of the content at that moment, not a live link.
- **Resume:** continue an old session. Fast because nothing is re-read, and risky for the same reason.
- **Fork:** branch one session into two so you can try two approaches from the same starting point. Watch for both branches acting on shared files.
- **Handover:** start a fresh session with a written summary. Anthropic's docs describe this as more robust than passing whole transcripts around.
- Rule of thumb: ask whether the files the session read have changed since. If yes, start fresh or re-read.

**Exam trap:** choosing resume for a long-running task when the underlying files have moved on.

### What the 7 videos actually teach

The series has a strong central idea:

> **LLMs are probabilistic; production systems must decide what the model may decide and what software must guarantee.**

That principle connects almost everything in the seven videos.

For example, suppose TalkProof has:

`Customer → Claude → refund decision`

A weak implementation says in the prompt:

> "Never refund more than £500."

The model will *usually* obey it. That's insufficient for a hard business rule.

A production design is:

```text
Claude proposes:
refund(customer, £700)
        ↓
Deterministic application code
        ↓
IF amount > £500 → REJECT
ELSE → execute
```

**Prompt = guidance.  
Code = enforcement.**

That is one of the most valuable lessons in this series.

### The most important technical mechanism is Videos 3–4

The phrase **"Claude doesn't run your tools"** sounds trivial, but it is fundamental.

Conceptually:

```text
YOUR APPLICATION
      │
      │ messages + available tools
      ▼
   CLAUDE API
      │
      │ "I want tool X called with Y"
      ▼
YOUR APPLICATION
      │
      │ actually executes X
      ▼
Database / API / filesystem / CRM / etc.
      │
      │ result
      ▼
YOUR APPLICATION
      │
      │ tool_result
      ▼
   CLAUDE API
      │
      ▼
 final answer / another tool request
```

The **agent** is therefore not simply "Claude".

It is the complete loop involving **model + orchestration code + tools + state/context + control logic**.

That distinction matters directly to the systems you've been reviewing.

## Video 6 explains another important production distinction

An HTTP/API request succeeding doesn't necessarily mean Claude completed the task.

For example:

```text
HTTP 200
   │
   ├── end_turn       → finished
   ├── tool_use       → execute requested tool
   ├── max_tokens     → NOT necessarily finished
   ├── pause_turn     → continuation required
   └── refusal        → handle explicitly
```

So application logic like:

```python
if response.status_code == 200:
    return response.text
```

can be conceptually wrong.

The orchestration layer must understand the **semantic state of the model response**, not merely transport success.

That's a real production-AI engineering concept, not certification trivia.
