Yes — this one is worth keeping. I checked the claim rather than treating the Short as authority. The core idea is real and traces to Andrej Karpathy's 2 Oct 2026 post: **writing → diagrams → interactive HTML → bespoke explainer video**. He specifically suggested ASD-STE100, sometimes softened to “80% of the way,” then diagrams, HTML, and finally 3Blue1Brown-style video with ElevenLabs or local TTS. citeturn0search1turn0search6 The broader point is more important than the individual tricks: as AI does more implementation work, the human bottleneck shifts toward **understanding, verification and oversight**.

For us, this connects directly to what we have been building. I would not treat these as four isolated prompts. I would treat them as a **comprehension ladder**:

1. **80% ASD-STE100** — default when I need to explain a difficult technical result clearly without making the prose robotic.
2. **Diagram** — when relationships, architecture, flow, sequence or causality matter more than prose.
3. **Interactive artifact** — when the user should manipulate assumptions. The SIP example is exactly right: sliders + year-by-year values + chart are better than a static explanation.
4. **Bespoke explainer video** — when a concept is important enough to learn deeply or communicate repeatedly. The model can generate the script, scenes, animation/code and narration pipeline; the human reviews the facts and teaching quality.

There is an important correction to the Short's framing: “80% ASD-STE100” is a **style heuristic**, not a measurable certification that the answer complies with 80% of the official aerospace standard. citeturn0search2 Also, a beautiful diagram, webpage or video can still contain a wrong explanation. Moving up the ladder improves comprehension; it does **not** replace source verification.

This is especially relevant to our AI learning system. We should test the same difficult concept at all four levels and measure which one actually helps you understand and recall it. I have therefore saved this as a reusable KB concept, not merely as a YouTube-tip note.

Yes. **This should become a reusable system, not something you keep typing.** Your Git Turn Protocol already says every project turn belongs in Git and v1.2 already handles parallel pages and multi-repo work. fileciteturn12file0L2-L2 What is missing is the layer **above** it: automatically deciding *which repo* owns the conversation and *which reusable skills* apply.

I would separate it into **two composable capabilities**, rather than one enormous prompt.

### 1. `Git Context Router` — almost always on

On the **first meaningful prompt of a new page**, it should inspect your accessible repos, their `AGENTS.md`, protocol pin, current state and handover. It proposes something like:

> **Detected topic:** AI-tool/LLM workflow research  
> **Proposed home:** `ai-tool-support-kb`  
> **Protocol:** Git Turn v1.2  
> **Apply Git-TURN automatically for the rest of this page?** Yes/No

You confirm **once**.

After that, you should **never have to write “do Git turn protocol” again on that page**.

Before every subsequent turn it silently asks:

**Does this still belong to the current repo?**

If yes → continue and Git-TURN automatically.

If the discussion changes from, say, AI-tool research to TalkProof development → **don't pollute `ai-tool-support-kb`**. Search your repos again, identify the TalkProof repo, and route the new work there. If uncertain between two repos, ask you once rather than guessing.

And if one message genuinely belongs to several repos, v1.2 already gives us P8: one home record and small pointer records in the other repos, with usage counted only once. fileciteturn12file0L2-L2

That is the architectural piece we were missing.

### 2. `Comprehension / Artifact Ladder` — invoked when useful

This is what today's Short triggered.

It shouldn't blindly make a video or HTML page every time. It chooses the **cheapest representation that substantially improves understanding**:

**Clear controlled prose → Diagram → Interactive artifact → Bespoke explainer video**

This can be used far beyond learning.

| Situation | Likely level |
|---|---|
| Quick explanation | Clear prose |
| Architecture / workflow / data flow | Diagram |
| ML model explanation | Prose + diagram |
| SIP/loan/pricing/cost simulator | Interactive |
| Product prototype | Interactive UI |
| API/system architecture | Diagram + interactive demo where useful |
| Debugging complicated execution | Sequence/flow diagram |
| Product requirements | Prose + workflow |
| Training/onboarding | Diagram → video |
| Important concept you repeatedly struggle with | Bespoke explainer |
| Demo to customers/investors | Interactive prototype + video |
| Comparing alternatives | Interactive comparison where worthwhile |

I **wouldn't** invoke the heavier levels for trivial questions, one-use answers, uncertain facts that first require verification, privacy-sensitive material that would cross a data boundary, or cases where fancy visuals could make a weak conclusion *look* authoritative.

ASD-STE100 itself should remain an **optional writing technique**, not become our universal writing style.

**Claude is currently the cleanest implementation.** Claude custom Skills are directories containing `SKILL.md`; Claude can automatically discover and invoke an appropriate skill when the task matches it. Project-level skills can live at `.claude/skills/<skill>/SKILL.md`, meaning the skill itself can be version-controlled in Git. citeturn0search1turn0search5turn0search9

**Gemini has Gems**, specifically designed to save repeatable detailed instructions so you don't repeatedly prompt the same behaviour. Files can also provide persistent context. citeturn0search0turn0search4

urlGoogle Gemini Gems guideturn0search0

**Perplexity Spaces** support custom instructions plus files, links and web sources. That's particularly useful for our *research/evidence* component, although I would not pretend it has committed something to Git unless its environment actually has Git write capability. citeturn0search7

For **ChatGPT**, we should implement the same logical router using persistent/custom instructions/workflows plus the GitHub connection when available. The important thing is that the canonical logic shouldn't live *only* inside ChatGPT.

For **Grok**, I want to verify its current supported customization/project mechanism before telling you exactly how we'll implement it. I don't want to invent feature parity.

### The more important design decision

Don't create five independently maintained prompts:

```text
ChatGPT prompt
Claude prompt
Gemini prompt
Perplexity prompt
Grok prompt
```

They'll drift.

Instead:

```text
                    CANONICAL GIT SPEC
                          │
             ┌────────────┴────────────┐
             │                         │
       Git Context Router       Reusable Skills
             │                         │
      ┌──────┼──────┬──────┐     ┌────┼────────┐
      ▼      ▼      ▼      ▼     ▼    ▼        ▼
   ChatGPT Claude Gemini Perplexity Learning Product Research
      │      │      │      │
   adapter SKILL   Gem    Space
```

**Git becomes the source of truth.**

Each AI gets only a thin adapter explaining how that AI should consume the canonical specification.
