## Which AI will we use (2 viable paths)

### Path A (Best “Atlassian-native” story): **Rovo Agent + Risk Engine**
- We build a **Rovo Agent** as part of the Forge app (Atlassian explicitly supports building Rovo agents with Forge). citeturn0search19turn0search26
- Our UI uses the Forge bridge **`rovo` API** to open Rovo chat sidebar and start an AI conversation with a pre-filled prompt (contextual assistant). citeturn0search11

**What AI does here:**
- Explains “why risk flagged” in human language
- Answers “what should I do now?” in-context inside Jira

**Hard truth:** Rovo Agent ≠ guaranteed available to every customer plan/site. If judges don’t have Rovo enabled, the “AI chat” layer may not work as a live feature. (We can still run the core risk detection without Rovo.)

---

### Path B (Most controllable + works anywhere): **External LLM API (OpenAI / Anthropic / etc.)**
- Forge can call external services, but you must **declare egress permissions** in the manifest for domains you call. citeturn0search0turn0search1turn0search7turn0search10
- This lets us use an LLM to generate:
  - risk explanations
  - concise summaries of sprint risk drivers
  - suggested mitigations

**Hard truth:** external LLM calls create compliance friction (data handling), cost, latency, and failure modes. Also you must be careful not to ship sensitive issue content to a third party.

---

## How AI is used (the “Risk Sentinel” design)

### Layer 1 — Deterministic risk detection (NOT LLM)
This is not “AI vibes.” This is **math + rules + signals**:

**Signals we compute from Jira:**
- Sprint scope growth rate (added after start)
- Spillover ratio (not done / committed)
- Blocker cluster density (many issues blocked by one dependency)
- Cycle time drift (WIP increasing, throughput dropping)
- SLA/duedate breach likelihood (based on remaining work vs velocity trend)
- Stale work (no updates for X days on critical issues)

**Output:** a numeric “Risk Score” + top drivers (explainable).

**Why this matters:** judges trust it because it’s transparent and repeatable.

---

### Layer 2 — AI explanation (LLM or Rovo Agent)
Once Layer 1 says “Risk is high,” we ask AI to produce:

- **Executive explanation**: “Risk is high because scope increased 28% after sprint start; 7 issues are blocked by X; cycle time increased from 2.1→3.4 days.”
- **Action suggestions**: “Split story ABC, escalate dependency DEF, freeze scope, re-estimate remaining work.”

This is where the AI shines: converting raw signals into readable actions.

---

## % AI usage (brutal + defendable)

If we build responsibly, the real split is:

- **70–85% of correctness/value** comes from deterministic detection (Layer 1).
- **15–30% of value** comes from AI explanation + summarization + suggested actions (Layer 2).

If we claim “100% AI,” we risk looking fake, because judges will ask:
> “So the LLM decides risk by itself? Based on what? How do you validate it?”

**So the winning framing is:**  
**AI is mandatory in the “human output layer,”** not the “truth layer.”

That still satisfies “AI-powered,” but avoids the “LLM hallucinated risk” trap.

---

## Why this pain still persists (even with Jira dashboards)

Because Jira is excellent at **tracking status**, but weak at **predicting trajectory**:
- Dashboards show “what is the state now,” not “what will happen if nothing changes.”
- Many teams don’t maintain fields cleanly (estimates, due dates, dependencies).
- Real risk lives in patterns across many issues (scope creep + blockers + throughput drift). Humans don’t see it early.

Also: Jira already has many reports, but **they are not proactive** and often not connected to “what to do next”.

---

## % pain covered (if we execute well)

### What we can realistically cover
- **60–75% of “surprise sprint failure” pain** for Scrum-ish teams that:
  - use sprints
  - have consistent statuses
  - update issues somewhat regularly

### What we will NOT cover well (and must admit)
- Teams with poor Jira hygiene (no estimates, no real sprint discipline): coverage drops to **20–40%**.
- Kanban-only teams: we can adapt, but sprint-based risk is weaker.
- Highly unique workflows where “blocked” isn’t tracked: blocker logic fails.

---

## Brutal failure modes (how this product can die)

1. **Data quality is trash** → risk detection becomes noisy → users ignore alerts.
2. **Too many alerts** → “alert fatigue” → app becomes background noise.
3. **Forge limits / scaling**: large Jira instances are hard to scan frequently. Scheduled triggers have limits (max 5 triggers; only one five-minute interval trigger). citeturn0search6turn0search13turn0search9
4. **Egress restrictions / security**: if we rely on external AI, we must declare egress + handle enterprise security concerns. citeturn0search0turn0search1turn0search7turn0search10
5. **“AI told me” is not acceptable**: if the app can’t justify why risk is high in concrete Jira facts, judges (and users) will reject it.

---

## The “WIN” version (how we avoid dying)
- Deterministic risk scoring first (explainable)
- AI only for explanation + recommended actions
- Strict throttling + only alert when risk crosses thresholds
- Incremental scanning (only changed issues since last run) to survive Forge constraints
