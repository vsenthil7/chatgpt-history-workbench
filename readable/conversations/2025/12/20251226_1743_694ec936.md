## 1) **Failure Mode Taxonomy (FINAL)**

All failures **must** be classifiable into exactly one of the following.  
Unclassifiable failure = **Critical by default**.

### **F1 — Soft Failure**
**Definition:**  
Degradation where **core safety, legality, and data integrity remain intact**.

**Examples:**
- Non-critical model timeout
- Partial upstream API latency
- UI rendering inconsistencies
- Non-authoritative data source unavailable

**System State:**
- Read-only or reduced functionality allowed
- No autonomous decision expansion
- No user-impacting irreversible actions

**Action:**
- Auto-retry within bounded limits
- Log + alert (non-paging)
- No human intervention required unless persistent

---

### **F2 — Hard Failure**
**Definition:**  
Loss of **reliability or correctness guarantees**, but **no confirmed breach**.

**Examples:**
- Model output confidence below threshold
- Inconsistent rule-engine resolution
- Data validation mismatch
- Audit trail write failure (temporary)

**System State:**
- Autonomous actions **suspended**
- Human-in-the-loop required
- System enters **Safe-Hold Mode**

**Action:**
- Immediate escalation to operator queue
- User-facing degradation notice
- No further processing until resolved or escalated

---

### **F3 — Critical Failure**
**Definition:**  
Any condition involving **legal risk, compliance breach, data exposure, or uncontrollable behavior**.

**Examples:**
- Unauthorized data access or leakage
- Regulatory constraint violation
- Policy contradiction with no safe resolution
- Model behavior outside bounded intent
- Tampering or integrity compromise

**System State:**
- **Immediate halt**
- Kill-switch eligible (see Section 4)
- System declared **UNSAFE**

**Action:**
- Kill-switch evaluation within same execution window
- Mandatory human authority intervention
- Incident log sealed and immutable

---

## 2) **Safeguard Triggers & Thresholds (LOCKED)**

| Trigger Category | Threshold Breach | Failure Class |
|-----------------|------------------|---------------|
| Confidence / Certainty | Below minimum bound | F2 |
| Policy Resolution | Ambiguous / conflicting | F2 → F3 |
| Audit Logging | Write failure > tolerance | F2 |
| Data Boundary | Cross-scope access | F3 |
| Compliance Check | Any violation | F3 |
| Human Override Ignored | Any instance | F3 |
| Kill-Switch Failure | Any malfunction | F3 |

**Rule:**  
Safeguards **must fail closed**, never open.

---

## 3) **Human Escalation & Intervention Rules**

### **Authority Levels**

1. **Operator**
   - Can resolve F1
   - Can review F2
   - Cannot override safeguards

2. **System Steward (Named Human Authority)**
   - Can resolve F2
   - Can recommend kill-switch
   - Can authorize restart post-incident

3. **Legal / Compliance Authority**
   - Required for any F3 resolution
   - Required for restart after kill-switch
   - Final authority on system validity

---

### **Escalation Logic**

- F1 → Operator (async)
- F2 → Immediate Operator + Steward
- F3 → Automatic escalation to Steward + Legal  
  No discretion. No delay.

---

## 4) **Kill-Switch Canon (AUTHORITY + LOGIC)**

### **Kill-Switch Definition**
A **non-negotiable mechanism** that halts:
- All autonomous processing
- All external calls
- All state mutations (except logging)

### **Kill-Switch Triggers**
Kill-switch **MUST activate** if:
- Any F3 is detected
- Failure cannot be classified within execution window
- Human override is unavailable or ignored
- Audit integrity is compromised
- Compliance signal is uncertain

---

### **Kill-Switch Authority**

- **Automatic:** System (for defined triggers)
- **Manual:** System Steward OR Legal Authority
- **Override:** **NONE**

Kill-switch **cannot be bypassed, delayed, or soft-disabled**.

---

## 5) **Graceful Degradation vs Hard Stop**

### **Graceful Degradation (Allowed)**
Only for **F1**:
- Reduced features
- Read-only responses
- Explicit uncertainty disclosures

### **Hard Stop (Mandatory)**
For **F2 unresolved** and **all F3**:
- No partial operation
- No shadow execution
- No background continuation

**Rule:**  
When in doubt → **Hard Stop**.

---

## 6) **Post-Incident Recovery & Restart Conditions**

### **Restart is ONLY allowed when:**
1. Failure is fully classified
2. Root cause documented
3. Safeguard updated or confirmed adequate
4. Audit trail validated
5. Human authority signs off (Steward + Legal for F3)

### **Prohibited:**
- Auto-restart after F3
- Silent recovery
- State rollback without audit continuity

---

## 7) **Invalidity Clause (LOCKED)**

If **any** of the following are true:
- Failure cannot be safely classified
- Safeguard trigger is ambiguous
- Kill-switch authority is unclear
- Restart conditions are unmet

👉 **The system is INVALID and must remain OFFLINE.**
