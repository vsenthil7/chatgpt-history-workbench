## ✅ What it’s about  
Uber describes “Genie” as an internal tool — essentially a generative-AI “copilot” for on-call engineering teams. The goal: help engineers and internal users ask questions (via Slack), get faster answers, reduce back-and-forth, and relieve burdens on human on-call responders. citeturn0view0turn0view0  

In more detail:  
- Many internal Slack channels at Uber get lots of questions from users asking for support from on-call engineering teams. citeturn0view0  
- The tool is built so that when a user requires help, they can ask via Slack and Genie uses large-language-model (LLM) + retrieval-augmented generation (RAG) methods to provide answers referencing Uber’s internal documentation. citeturn0view0turn0view0  
- They chose a RAG (retrieval + generation) approach rather than fine-tuning a model from scratch, because RAG allowed faster time-to-market and needed fewer full “example” data sets. citeturn0view0

## 🔍 How it works (architecture)  
The blog post provides a “deep dive” into how the system is built:

- They ingest internal knowledge sources: Uber’s internal wiki (“Engwiki”), internal Stack Overflow instances, engineering requirement docs, etc. citeturn0view0  
- These are chunked and embedded (vectorised) using an embedding model (OpenAI embedding) and stored in a vector database. citeturn0view0  
- When a user asks a question in Slack, that query is also embedded; the system retrieves relevant knowledge chunks from the vector DB; those become the “context” for the LLM response. citeturn0view0  
- They mention various components: ETL (extract/transform/load) stage using Apache Spark, indexing, pushing data to “Terrablob” (Uber’s internal blob storage) and “Sia” (Uber’s internal vector-db solution) for serving. citeturn0view0  
- They track cost, usage, and maintain a feedback loop: users can mark replies as “Resolved”, “Helpful”, “Not Helpful”, “Not Relevant” within Slack; this feedback is collected via Kafka to Hive tables and dashboards. citeturn0view0  
- To reduce hallucination (i.e., incorrect answers), they embed the source URL and sub-context into the prompt, instructing the LLM to only answer from those sources and provide citations. citeturn0view0  
- They also restrict what data sources are used (to avoid leaking overly sensitive internal info) and design an interaction mode in Slack so if Genie can’t fully answer, escalation to a human on-call engineer is easy. citeturn0view0

Here’s the “full tech architecture” of Uber’s **Genie** (their Gen-AI on-call copilot) distilled from the blog, plus a plain-English walkthrough of each block, and a risk/limitations checklist.

# What the architecture shows (Figure 3) — end-to-end flow
1) **Internal knowledge sources → ETL (Spark)**  
   Uber scrapes/loads Engwiki (internal wiki), internal Stack Overflow, engineering docs, etc., into Spark dataframes. This is the *data prep* stage (source URL + content + metadata). citeturn0view0

2) **Embedding generation → Terrablob (blob storage)**  
   Document chunks are created (via LangChain), embeddings are generated with OpenAI (via PySpark UDFs), and both content chunks + vectors are written to **Terrablob** (Uber’s internal blob store). Access to embeddings is scoped to relevant Slack channels. citeturn0view0

3) **Index build & push → Sia (vector DB)**  
   A “bootstrap” job ingests into **Sia** (Uber’s in-house vector database). Two Spark jobs build/merge the index and publish snapshots to Terrablob. Each “leaf” node syncs the base index + snapshot; queries are fanned out to leaves for retrieval. citeturn0view0

4) **Knowledge Service (back end)**  
   Incoming user questions (from Slack) are embedded; the service fetches top-k chunks from Sia; those chunks become **prompt context** (“sub-contexts” with source URLs) passed to the LLM. citeturn0view0

5) **LLM via Michelangelo Gateway + cost tracking**  
   Requests carry a UUID from Slack → Knowledge Service → **Michelangelo Gateway** (pass-through to the LLM) so costs and audit logs can be attributed by UUID. citeturn0view0

6) **Slack UX + human escalation**  
   Genie posts an answer in Slack with buttons for **Resolved / Helpful / Not Helpful / Not Relevant** and quick **escalation to on-call** if needed. citeturn0view0

7) **Feedback & evaluation pipelines**  
   Button clicks flow through a Slack plugin into Kafka → Hive for dashboards. Separate evaluation ETL lets teams run “LLM-as-a-judge” checks on answer quality (e.g., hallucination, relevancy) and even evaluate **document quality** itself. Reports are exposed in the Michelangelo UI. citeturn0view0

# Components explained (what each block does)

- **Engwiki, Internal Stack Overflow, Eng docs** – Primary corpora that hold answers to recurring support questions. citeturn0view0  
- **Spark ETL (Data Prep)** – Fetch APIs/files, normalize into a dataframe schema: source URL, content, and metadata. citeturn0view0  
- **Chunking + OpenAI Embeddings (via PySpark UDFs)** – Split long docs into smaller passages; compute vector embeddings per chunk; write artifacts to Terrablob. citeturn0view0  
- **Terrablob (Blob Storage)** – Stores embedding artifacts, base indexes, snapshots that the vector infra consumes. citeturn0view0  
- **Sia (Vector DB)** – Uber’s in-house vector search. Leaf nodes sync index snapshots; queries broadcast to leaves for fast nearest-neighbor retrieval. citeturn0view0  
- **Knowledge Service** – Gateway that embeds the incoming Slack question, retrieves top chunks from Sia, and constructs an LLM prompt that *must* answer using supplied sub-contexts and cite their URLs. citeturn0view0  
- **Michelangelo Gateway (LLM pass-through)** – Routes prompts to the chosen LLM and propagates a UUID for **cost/audit** tracking. citeturn0view0  
- **Slack Client UX** – Presents the answer and provides one-click actions (Resolved/Helpful/Not Helpful/Not Relevant) and **escalate to human on-call**. citeturn0view0  
- **Metrics & Eval (Kafka → Hive → Dashboards)** – Ingests feedback events; teams can run custom evals (LLM-as-judge) on Genie’s responses *and* on **document quality** to improve the KB. citeturn0view0

# Guardrails the blog calls out (how they reduce bad answers)

- **Prompting with sub-contexts + mandatory citations** – Genie injects retrieved *sub-contexts* and asks the LLM to answer *only* from them and to **return source URLs**. This aims to curb hallucination. citeturn0view0  
- **Curated data sources** – Only broadly accessible internal sources are used to avoid leaking sensitive content into Slack or to external model providers. citeturn0view0  
- **Interaction design** – Buttons encourage follow-ups or quick escalation when Genie can’t help. citeturn0view0

# Risks & limitations

**Explicit in the blog (or strongly implied):**
- **Hallucination risk remains** (mitigated, not eliminated): even with RAG, incorrect or over-confident answers can slip through; thus evals, citations, and human escalation exist. citeturn0view0  
- **Documentation quality is a hard ceiling**: poor, outdated, or inconsistent docs will cap answer quality; hence the separate **document evaluation** pipeline. citeturn0view0  
- **Data exposure constraints**: only certain sources are allowed; over-restricting sources can reduce coverage; under-restricting raises leakage risk. citeturn0view0  
- **User-experience dependency**: Slack channel norms and adoption influence success; Genie needs crisp questions and users willing to click feedback. citeturn0view0

**Additional practical risks (inferred best-practice concerns):**
- **Prompt-injection in docs**: Malicious or poorly formatted internal pages could try to steer the LLM. Content sanitization and retrieval-time filters are needed. (Inference)  
- **RAG retrieval failure modes**: Embedding drift, bad chunking, or suboptimal top-k can return irrelevant slices → wrong answers. Continuous eval/tuning is required. (Inference)  
- **Index freshness & scale**: High-churn docs require frequent re-indexing; Sia leaf syncs and snapshot management must keep up under load. (Inference)  
- **Latency & cost spikes**: Vector search + LLM calls can be costly at Slack scale; mis-scoped UUID tracking, retry storms, or long contexts can balloon costs/latency. (Inference based on their cost-tracking emphasis.) citeturn0view0  
- **Access control consistency**: Slack channel membership ≠ data entitlements; enforcing per-source ACLs at retrieval/prompt time is non-trivial. (Inference)  
- **LLM-as-Judge biases**: Automated evals can encode model bias; human spot-checks and task-specific metrics are still needed. (Inference)  
- **Operational coupling**: Reliance on Slack, Sia, Terrablob, Michelangelo, and OpenAI means any outage or API change can degrade Genie’s service quality. (Inference)
